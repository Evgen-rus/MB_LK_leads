# План разбора проблемы с DB pool / долгими Session

Короткая рабочая памятка, чтобы потом быстро вернуться к проблеме `QueuePool limit ... connection timed out`.

## Что уже известно

По логам от `2026-04-18` backend падал в webhook-обработчике не из-за данных лида, а из-за нехватки соединений к БД:

- ошибка: `sqlalchemy.exc.TimeoutError: QueuePool limit ... connection timed out`
- контур: `POST /api/provider-test/{secret}`
- точка падения: первый запрос к БД в `crud.get_provider_lead_by_vid(...)`

Важно: это больше похоже не на "сломанный webhook", а на то, что в момент пика backend не смог получить свободное соединение из пула.

## Что уже сделано как временная защита

В `.env` уже выставлены:

- `DB_POOL_SIZE=10`
- `DB_MAX_OVERFLOW=20`
- `DB_POOL_TIMEOUT=30`

Это должно смягчить короткие пики нагрузки, но не устраняет причину, если где-то сессии живут слишком долго.

## Главная гипотеза

Явной утечки вида "открыли `SessionLocal()` и забыли закрыть" пока не видно.

Самый вероятный корень проблемы:

- request-scoped `db_sess` или одна длинная `SessionLocal()`
- живёт слишком долго
- при этом внутри идут внешние вызовы `Prostats` / `Telegram`
- местами ещё и `sleep/retry`

То есть основная проблема похожа на **долгое удержание session/connection**, а не на прямую утечку.

## Самые подозрительные места в коде

### 1. `backend/app/main.py` -> `run_limit_control_loop`

Почему опасно:

- одна `SessionLocal()` открывается на весь проход цикла
- внутри обрабатываются все клиенты подряд
- на этой же сессии вызывается `_run_limit_control_for_client(...)`

Риск: высокий.  
Тип: долгое удержание.

### 2. `backend/app/main.py` -> `_run_limit_control_for_client`

Почему опасно:

- функция делает несколько DB-операций
- затем вызывает внешние действия через `Prostats`
- затем открывает дополнительные короткие сессии на запись

Отдельно важно: там есть комментарий про "не держать соединение во время сети", но далее всё равно используется тот же `db_sess` в соседней логике.

Риск: высокий.  
Тип: долгое удержание.

### 3. `backend/app/main.py` -> `_sync_client_tariff_signal_alert`

Почему опасно:

- получает уже существующий `db_sess`
- читает тариф из БД
- потом вызывает `notifications.send_system_notification(...)`
- это Telegram-сеть при живой сессии

Важно:

- если `NOTIFICATIONS_TELEGRAM_ENABLED=False`, то реальный сетевой вызов в Telegram не выполняется
- в таком режиме текущий runtime-риск здесь заметно ниже
- но архитектурно место всё равно остаётся потенциально опасным, если Telegram снова включат

Риск: высокий при включённом Telegram, низкий/средний при `NOTIFICATIONS_TELEGRAM_ENABLED=False`.  
Тип: долгое удержание.

### 4. `backend/app/main.py` -> `_create_projects_with_unique_names`

Почему опасно:

- после `db_sess.flush()` вызывается rename у Prostats
- дальше возможны retry
- в этой цепочке есть сетевые вызовы
- при проблемах это может тянуться заметно дольше обычного

Риск: высокий.  
Тип: долгое удержание.

### 5. `backend/app/main.py` -> `_rename_project_in_prostats_with_retries`

Почему опасно:

- retry-логика по внешнему API
- есть `sleep` между попытками
- если эта функция вызвана в контексте живой DB-сессии, соединение может удерживаться слишком долго

Риск: высокий.  
Тип: долгое удержание.

### 6. `backend/app/main.py` -> `create_projects`

Почему опасно:

- request `db_sess` живёт на весь endpoint
- после создания проектов вызывается `_run_limit_control_for_client(db_sess, ...)`
- один HTTP-запрос начинает включать и БД, и Prostats, и лимит-контроль

Риск: средний/высокий.  
Тип: долгое удержание.

### 7. `backend/app/main.py` -> `update_project`, `delete_project`, `admin_delete_project`

Почему опасно:

- request `db_sess` остаётся жить до конца handler
- перед `Prostats` есть `rollback()`, но не происходит полного закрытия сессии
- это лучше, чем держать активную транзакцию, но хуже, чем полностью разнести read/network/write по отдельным коротким сессиям

Риск: средний.  
Тип: долгое удержание.

### 8. `backend/app/main.py` -> `admin_pause_client_projects`, `admin_resume_client_projects`

Почему опасно:

- один handler
- цикл по проектам
- внутри последовательные вызовы `Prostats`
- исходный `db_sess` живёт всё это время

Риск: средний.  
Тип: долгое удержание.

## Что не выглядит как явная утечка

### `backend/app/main.py` -> `get_db`

Здесь паттерн нормальный:

- `db_sess = SessionLocal()`
- `yield`
- `finally: db_sess.close()`

То есть базовый dependency сам по себе не выглядит источником утечки.

### `with SessionLocal() as ...`

Во многих местах код использует короткие `with SessionLocal() as ...`, и это как раз хороший паттерн.

Проблема чаще не в отсутствии `close()`, а в том, что некоторые длинные сценарии держат одну и ту же сессию слишком долго.

## Что делать потом, когда вернусь к задаче

Ниже порядок действий от самого полезного к менее срочному.

### Шаг 1. Разрезать длинную сессию в `run_limit_control_loop`

Цель:

- не держать одну `SessionLocal()` на весь батч клиентов

Идея:

- одной короткой сессией получить список `client_ids`
- дальше для каждого клиента открывать отдельную короткую сессию

Ожидаемый эффект:

- фон не будет так долго занимать пул
- меньше шанс, что webhook упрётся в пустой pool

### Шаг 2. Убрать Telegram из жизни той же DB-сессии

Цель:

- `db_sess` не должен жить во время `send_system_notification(...)`

Идея:

- нужные данные читаются в короткой сессии
- сессия закрывается
- потом идёт Telegram
- при успехе отдельная короткая сессия обновляет флаг/уровень

Ожидаемый эффект:

- сеть перестанет удерживать pool

### Шаг 3. Разнести read / network / write в unique project flow

Цель:

- не держать `db_sess` во время retry/sleep/Prostats rename

Идея:

- короткая сессия для чтения/подготовки
- сетевой вызов без живой DB-сессии
- затем отдельная короткая сессия для фиксации результата

Ожидаемый эффект:

- уменьшение длительности удержания соединений в одном из самых тяжёлых сценариев

### Шаг 4. Проверить manager endpoints с циклами по проектам

Сначала смотреть:

- `admin_pause_client_projects`
- `admin_resume_client_projects`
- похожие места, где внутри handler есть цикл + `Prostats`

Цель:

- не держать один `db_sess` на весь длинный сетевой сценарий

### Шаг 5. При желании добавить временную диагностику

Если проблема повторится, полезно временно залогировать:

- старт/конец limit-control прохода
- сколько клиентов обрабатывается в одном цикле
- сколько времени занимает `_run_limit_control_for_client`
- сколько времени занимают вызовы `Prostats`
- сколько времени занимает Telegram-отправка

Это даст ответ, где именно backend "залипает" дольше всего.

## Какой фикс делать первым

Если времени мало, самый полезный первый фикс:

1. `run_limit_control_loop`
2. `_sync_client_tariff_signal_alert`
3. `_create_projects_with_unique_names`

Именно эти места сейчас выглядят самыми вероятными источниками долгого удержания сессий.

## Как понимать результат после правок

Признаки, что стало лучше:

- в логах исчезли `QueuePool timeout`
- webhook перестал массово отдавать `499` после подвисаний
- меньше длинных запросов в `app.access`
- фоновые limit-control проходы не создают каскад ошибок в API

## Риск-оценка

- поднять pool-настройки в `.env`: низкий/средний риск, временная защита
- разрезать длинные сессии в фоне: низкий/средний риск, полезно
- перестроить unique project flow: средний риск, потому что там есть важная бизнес-логика и retry

## Короткий вывод

Сейчас картина такая:

- настройки пула уже стали лучше
- явная утечка сессий не найдена
- основная проблема, вероятнее всего, в долгом удержании `Session` во время сети и retry

Значит следующий правильный шаг — не просто ещё сильнее увеличивать пул, а постепенно укорачивать жизнь DB-сессий в самых тяжёлых местах.
