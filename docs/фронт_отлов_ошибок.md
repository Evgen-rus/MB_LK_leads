1) В браузере:
   - F12 → Console: runtime-ошибки и предупреждения React/JS, сетевые ошибки.
   - F12 → Network: смотреть ответы API (4xx/5xx, тело ответа), время отклика.
   - React DevTools (расширение браузера) — видеть дерево компонентов, стейт/пропсы, Suspense/ошибки рендеринга.

2) В процессе разработки:
   - Локальный dev-сервер (`npm run dev`) в отдельном терминале: ошибки сборки, горячая перезагрузка, предупреждения Vite/ESLint.
   - TypeScript строгость: держать `strict` в tsconfig, не использовать `any`; ловит несостыковки типов до рантайма.
   - ESLint + React hooks правила: предотвращают ошибки с зависимостями эффектов.

3) Тесты:
   - Unit/компонентные тесты (Jest + React Testing Library): проверять логику и рендер ключевых компонентов.
   - Интеграционные/скриншотные (Playwright/Cypress) — сценарии кликов и формы; помогают ловить регрессии.

4) Отлов ошибок в рантайме:
   - Global error boundary в React (ErrorBoundary) — отлавливать падения в дереве компонентов, показывать дружелюбное сообщение, отправлять отчёт.
   - Логгер клиентских ошибок (у тебя есть `logger.ts` + `sendClientError`): включить отправку в проде и, при необходимости, в dev через `VITE_REPORT_ERRORS=true`.
   - `window.onerror` / `unhandledrejection` — уже есть в `logger.ts`, можно убедиться, что отчёты доходят.

5) Метрики и мониторинг (в проде):
   - Sentry / LogRocket / Bugsnag — сбор JS-ошибок с трейсами, пользователем, браузером.
   - Performance API / Web Vitals — CLS/LCP/FID, но это следующий шаг.

6) Проверка API-контрактов:
   - Если есть OpenAPI/Swagger — генерировать типы клиента; меньше рассинхронов.
   - При ошибке API — выводить текст из `errorDetail`/`message` (мы уже добавили `getErrorMessage`).

7) CI:
   - На CI гонять: `npm run lint`, `npm run build`, тесты (`npm test`/`npm run test:e2e`).
   - Опционально: `npm run typecheck` (tsc --noEmit) отдельно, чтобы ловить типовые ошибки без сборки.

## Что такое runtime-отчеты ошибок?

**Runtime-отчеты** - это система автоматического сбора и отправки JavaScript-ошибок с фронтенда на бэкенд. Когда в браузере происходит ошибка, она автоматически отправляется на сервер и логируется.

### Как это работает:

1. **В коде** (`logger.ts`) есть обработчики:
   - `window.onerror` - ловит необработанные ошибки
   - `window.unhandledrejection` - ловит необработанные промисы

2. **По умолчанию** отчеты работают только в **production** (на сайте leadrecordwh.ru)

3. **Для разработки** их можно включить через переменную окружения `VITE_REPORT_ERRORS=true`

4. **Куда отправляется**: в бэкенд на эндпоинт `/client-errors`, где ошибки логируются в файл `logs/app.log`

## Как включить и проверить

### Шаг 1: Создать файл `.env.local`
В папке `my-app-vite/` создай файл `.env.local` с содержимым:

```
VITE_REPORT_ERRORS=true
```

### Шаг 2: Проверить что отчеты срабатывают

Запусти dev-сервер:
```bash
cd my-app-vite
npm run dev
```

### Шаг 3: Проверить в браузере

1. Открой браузер на `http://localhost:5173`
2. Открой **F12 → Console**
3. Создай тестовую ошибку - в консоли выполни:
   ```javascript
   throw new Error('Тестовая ошибка для проверки отчетов');
   ```

### Шаг 4: Проверить логи на сервере

Если бэкенд запущен, посмотри в файл `logs/app.log` - должна появиться запись типа:
```
frontend_error level=error url=http://localhost:5173 ua=... msg=Тестовая ошибка для проверки отчетов rid=...
```

## Где смотреть ошибки

- **В браузере**: F12 → Console (красные ошибки)
- **В логах бэкенда**: `logs/app.log` - ищи записи с `frontend_error`
- **В production**: ошибки автоматически собираются в логи сервера

## Что передается в отчет

Из `api.ts` видно что `sendClientError` отправляет:
- `message` - текст ошибки
- `stack` - стек вызовов 
- `url` - адрес страницы где произошла ошибка
- `userAgent` - информация о браузере
- `level` - уровень ошибки (error/warn/info)
- `time` - время в ISO формате

Это поможет тебе отслеживать какие ошибки происходят у пользователей в реальном использовании приложения.
