## 🔌 Вебхук провайдера (provider leads)

### Назначение
Принимает лиды от провайдера и сохраняет их в новую таблицу `provider_leads`.

### Эндпоинт
- `POST /api/provider-test/{WEBHOOK_SECRET}`
- Секрет берётся из `.env` (`WEBHOOK_SECRET`)

### Логирование
- Лог: `logs/provider_webhook.log`
- Ротация: раз в сутки, хранение 30 дней

### Таблица `provider_leads`
Основные поля:
- `vid` — уникальный внешний ID (дедупликация по нему)
- `phone` — строка (если несколько телефонов, объединяем через запятую)
- `phones_raw` — JSON‑массив исходных телефонов
- `project_name` — название проекта из `page`
- `prov_created_at` — время из `time` (MSK)
- `prov_chanel` — `B1/B2/B3/B4` из начала `page`
- `prov_source` — часть после второго `_` в `page` (если есть)
- `subdomain` — если пришло в payload
- `imported_at` — время записи в БД (MSK)
- `project_id` — сопоставляется по `projects.name == project_name` (может быть `NULL`)

### nginx (прокси)
Пример прокси для вебхука:
```nginx
location /api/provider-test/<secret> {
    proxy_pass http://127.0.0.1:8000/api/provider-test/<secret>;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

### Решение по уникальной привязке лидов для новых проектов (пока без внедрения в код)

Статус: согласованный подход для следующей реализации.

Проблема:
- Провайдер в webhook не передаёт `project_id`.
- Привязка по `projects.name == page` ломается при дублях имён.

Принятое направление:
- Для новых проектов в имя, отправляемое провайдеру, добавляется технический LR-токен.
- Старые проекты не переименовываем и не мигрируем.

Формат имени (пример):
- `B1_[LR00000200000034] Эпкара вилочники`
- `B2_[LR00000200000035] Эпкара вилочники`
- `B3_[LR00000200000036] Эпкара вилочники`

Где:
- `LR` — префикс технического идентификатора.
- первые `6` цифр — `client_id` с `0`-padding.
- следующие `8` цифр — `project_id` с `0`-padding.

Почему именно фиксированная длина:
- Вариант `[LRidклиентаidпроекта]` без разделителей и фиксированной длины может давать коллизии.
- Пример коллизии: `(client_id=1, project_id=234)` и `(client_id=12, project_id=34)` -> одинаковый токен `LR1234`.
- Фиксированная длина делает токен однозначным и уникальным.

Ограничения:
- Внутри LR-токена не использовать `_`, чтобы не ломать текущий парсер `page` по `_`.
- Токен должен генерироваться backend и быть неизменяемым.
- Человеческое название проекта остаётся видимым клиенту (токен не скрываем).

### Компактный вариант (добавлен как предпочтительный):
- `B1_[LR34] Эпкара вилочники`
- `B2_[LR35] Эпкара вилочники`
- `B3_[LR36] Эпкара вилочники`

Правило:
- В токене используется только `project_id` (например, `LR34`).
- Этого достаточно для уникальности, так как `project_id` — уникальный первичный ключ проекта.
- `client_id` можно не добавлять в токен, потому что клиент однозначно определяется через связь проекта (`projects.user_id`).

Опционально (для фиксированной длины):
- использовать `project_id` с `0`-padding, например `LR000034`.

Если уже занято до 1000+, лучший практичный вариант:

использовать токен LR{project_id} без ограничений по длине (LR1001, LR15234 и т.д.),
или для аккуратной сортировки сразу ввести фиксированную длину 6:
LR001001, LR015234.
Рекомендую второй вариант (6 цифр), потому что:

визуально ровно,
корректно сортируется как строка,
запаса хватает до 999999 проектов.
Итоговый шаблон:

B1_[LR001001] Эпкара вилочники
B2_[LR001002] Эпкара вилочники

### еще вариант в карточке клиента назначаем [LR...]
Да, такой формат тоже рабочий:

`B1_[LR150] id35 Эпкара вилочники`

Он не ломает текущий разбор канала (`B1_...`) и даёт уникальность за счёт `id35` (если это ваш реальный `project_id`).

Чтобы было надёжно в долгую, лучше стандартизировать маркер проекта чуть жёстче:
- `B1_[LR150] [P35] Эпкара вилочники`  
или  
- `B1_[LR150] pid35 Эпкара вилочники`

Почему: `id35` в свободном тексте сложнее стабильно парсить.

Обязательные правила:
1. `project_id` вставляет только backend.
2. Пользователь не редактирует этот технический фрагмент.
3. На webhook делаете парсинг по регулярному шаблону, иначе fallback в “неоднозначный лид/карантин”.
