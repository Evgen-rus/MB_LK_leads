# Концепция админского дашборда ЛК

Дата: 2026-05-14

## 1. Цель

Добавить в админский личный кабинет отдельный раздел `Дашборд`, который показывает руководителю бизнеса ключевую картину по работе ЛК: клиенты, проекты, полученные данные, тарифы, остатки, риски и точки, требующие внимания.

Дашборд не должен заменять существующие разделы `Клиенты`, `Проекты`, `Лиды`, `Отчёты`, `История`. Его задача — быстро ответить на вопросы:

- что происходит сейчас;
- где есть риск остановки или перерасхода;
- какие клиенты и проекты требуют внимания;
- как меняется объём данных за день, неделю и месяц;
- куда перейти для детальной проверки.

## 2. Роль пользователя

Первый этап — дашборд только для админа.

Админ в этом сценарии — руководитель всего бизнеса, который управляет ЛК, клиентами, агентами, проектами, тарифами, остатками клиентов и операционными рисками.

Важно: дашборд строится только в рамках текущей работы ЛК. Мы не добавляем отдельную CRM, финансовую аналитику вне существующих данных, внешнюю BI-систему или новые бизнес-процессы. Используем данные, которые уже есть или логически следуют из текущих сущностей ЛК.

## 3. Основные показатели

### Верхний блок KPI

В верхней части экрана предлагается показать основные карточки:

- `Всего клиентов`
- `Всего проектов`
- `Активные проекты`
- `Проекты на паузе`
- `Проекты в блокировке оператора`
- `Суммарный остаток клиентов`

Дополнительно можно показывать изменение к предыдущему периоду, если это будет полезно:

- `+/- к вчера`
- `+/- к прошлой неделе`
- `+/- к прошлому месяцу`

Но на первом этапе лучше не перегружать экран и сначала согласовать базовые цифры.

## 4. Полученные данные за периоды

Отдельный блок должен показывать, сколько данных получено:

- `за вчера`
- `за последние 7 дней`
- `за текущий месяц`

Под "данными" нужно согласовать точное значение. В рамках текущего ЛК наиболее логично считать это количеством полученных provider leads, то есть записей в `provider_leads`.

Возможное отображение:

- три KPI-карточки: `Вчера`, `7 дней`, `Месяц`;
- график динамики по дням;
- переключатель периода: день / неделя / месяц;
- разбивка по источникам `A/B/C/D` во frontend, при сохранении raw-кодов `B1/B2/B3/B4` в backend.

## 5. Контроль тарифов и остатков клиентов

Нужен отдельный блок "Клиенты с риском по остатку".

Так как в текущей архитектуре основной контур контроля — это клиентские тарифы и обязательные сигналы `signal1`, `signal2`, `signal3`, дашборд должен опираться не на старые проценты лимита проекта, а на текущий остаток клиента относительно настроенных сигналов последнего тарифа.

Предлагаемые категории:

1. `Ниже signal3`
   - самая критичная зона;
   - клиент уже пересёк нижний порог остатка;
   - требует первоочередного внимания.

2. `Ниже signal2`
   - средняя зона риска;
   - из этого списка нужно исключить клиентов, которые уже попали в `Ниже signal3`.

3. `Ниже signal1`
   - раннее предупреждение;
   - из этого списка нужно исключить клиентов, которые уже попали в `Ниже signal2` или `Ниже signal3`.

Пример логики:

- если у клиента остаток 400, `signal3 = 500`, `signal2 = 1000`, `signal1 = 2000`, клиент попадает только в `Ниже signal3`;
- если остаток 800, клиент попадает только в `Ниже signal2`;
- если остаток 1500, клиент попадает только в `Ниже signal1`;
- один клиент не должен дублироваться в нескольких группах, потому что дашборд должен показывать его в самой критичной достигнутой зоне.

Для каждого клиента в списке желательно показывать:

- клиент;
- агент, если клиент закреплён за агентом;
- текущий остаток;
- текущий тариф;
- значения `signal1`, `signal2`, `signal3`;
- достигнутый уровень сигнала;
- дата последнего тарифа;
- активные проекты клиента;
- быстрый переход к клиенту, тарифам, балансу и проектам.

## 6. Блоки, требующие внимания

Отдельный блок должен показывать не просто статистику, а проблемы и риски:

- клиенты ниже `signal3`;
- клиенты ниже `signal2`, без клиентов из группы `signal3`;
- клиенты ниже `signal1`, без клиентов из групп `signal2` и `signal3`;
- проекты в статусе `Блокировка оператора`;
- клиенты с низким остатком;
- лиды без привязки к проекту;
- неоднозначные привязки лидов к проектам;
- ошибки операций с проектами;
- клиенты без активности за выбранный период.

Этот блок должен быть ближе к началу экрана, потому что руководителю важно быстро понять, где нужно действие.

## 7. Графики и диаграммы

Для первого этапа предлагаются такие визуализации:

### Динамика полученных данных

График по дням:

- количество лидов / данных по каждому дню;
- возможность выбрать период: 7 дней, 30 дней, текущий месяц;
- сравнение с предыдущим периодом можно добавить позже.

### Данные по источникам

Диаграмма или горизонтальные бары:

- `A`
- `B`
- `C`
- `D`

Важно: это только frontend-отображение. В API, БД, webhook, XLSX и Prostats остаются `B1`, `B2`, `B3`, `B4`.

### Топ клиентов

Таблица или горизонтальный рейтинг:

- топ клиентов по количеству полученных данных;
- топ клиентов по расходу;
- топ клиентов по количеству активных проектов.

### Статусы проектов

Диаграмма распределения проектов:

- активные;
- на паузе;
- удалённые;
- блокировка оператора;
- другие статусы, если они используются в текущем ЛК.

## 8. Как пользователь взаимодействует с дашбордом

Пользователь заходит в админский ЛК и видит в боковом меню отдельный раздел `Дашборд`.

Первый экран должен работать как управленческая панель:

1. Сначала админ видит общую картину:
   - сколько клиентов;
   - сколько проектов;
   - сколько данных пришло за вчера, неделю и месяц;
   - сколько проектов находится в рисковых статусах.

2. Затем админ смотрит блок "Требует внимания":
   - клиентов ниже `signal3`;
   - клиентов ниже `signal2`;
   - клиентов ниже `signal1`;
   - блокировки оператора;
   - ошибки и непривязанные лиды.

3. Если проблема требует проверки, админ кликает по строке или кнопке:
   - проект открывается в разделе проектов;
   - клиент открывается в карточке клиента;
   - лиды открываются в таблице лидов с нужным фильтром;
   - история открывается в карточке события.

4. Админ может менять период:
   - вчера;
   - 7 дней;
   - месяц;
   - произвольный период позже, если потребуется.

5. Админ может фильтровать данные:
   - по клиенту;
   - по агенту;
   - по источнику;
   - по статусу проекта.

6. Дашборд не должен заставлять пользователя вручную собирать выводы из разных таблиц. Он должен сам подсвечивать приоритет:
   - сначала клиентов ниже `signal3`;
   - затем клиентов ниже `signal2`;
   - затем клиентов ниже `signal1`;
   - затем технические и операционные проблемы;
   - затем общая статистика и динамика.

## 9. Рекомендуемая структура экрана

Предлагаемый порядок блоков:

1. Фильтры:
   - период;
   - клиент;
   - агент;
   - источник.

2. Главные KPI:
   - всего клиентов;
   - всего проектов;
   - данные за вчера;
   - данные за неделю;
   - данные за месяц;
   - суммарный остаток клиентов.

3. Требует внимания:
   - клиенты ниже `signal3`;
   - клиенты ниже `signal2`, без клиентов из группы `signal3`;
   - клиенты ниже `signal1`, без клиентов из групп `signal2` и `signal3`;
   - блокировка оператора;
   - ошибки и непривязанные лиды.

4. Графики:
   - динамика полученных данных;
   - распределение данных по источникам;
   - распределение проектов по статусам.

5. Рейтинги:
   - топ клиентов по данным;
   - топ клиентов по расходу;
   - топ клиентов по активным проектам.

## 10. Важные ограничения проекта

При реализации нужно учитывать текущую архитектуру ЛК:

- админ определяется как `user.id == 1`, но также учитывается роль `admin`;
- frontend показывает источники как `A/B/C/D`, backend работает с `B1/B2/B3/B4`;
- нельзя рассчитывать права только на frontend;
- данные для дашборда нужно считать на backend, чтобы не загружать большие списки во frontend;
- даты и отчёты должны учитывать `SHEETS_TZ`;
- статус `Блокировка оператора` является системным и не должен становиться ручным статусом выбора;
- текущие риски по остаткам нужно считать через тарифный контур клиента: последний тариф, текущий `remaining` и пороги `signal1/signal2/signal3`;
- не нужно менять существующую бизнес-логику проектов, тарифов, webhook или импорта ради первого этапа дашборда.

## 11. Возможная backend-структура

Предварительно можно сделать отдельные endpoint-ы:

- `GET /admin/dashboard/summary`
- `GET /admin/dashboard/received-data`
- `GET /admin/dashboard/tariff-signals`
- `GET /admin/dashboard/project-statuses`
- `GET /admin/dashboard/source-breakdown`
- `GET /admin/dashboard/client-rankings`
- `GET /admin/dashboard/attention`

Можно также начать с одного агрегирующего endpoint-а:

- `GET /admin/dashboard`

Для первого этапа один endpoint может быть проще. Если данных станет много или графики будут обновляться независимо, можно разделить на несколько endpoint-ов.

Ответ: только успешно привязанные к проекту лиды
Если есть не привязаные к проекту лиды нужно както их подсвечивать наверное количество просто их писать, это может быть если сбой какойто

Последние 30 дней

последние 7

Предупреждение/Риск/Критично

да

## 13. Предлагаемый первый этап

Для первой версии админского дашборда предлагается сделать:

- отдельный раздел `Дашборд` в меню админа;
- KPI: всего клиентов, всего проектов, данные за вчера, данные за неделю, данные за месяц;
- блок клиентов ниже `signal3`;
- блок клиентов ниже `signal2`, исключая клиентов ниже `signal3`;
- блок клиентов ниже `signal1`, исключая клиентов ниже `signal2` и `signal3`;
- график динамики данных по дням;
- разбивку данных по источникам;
- распределение проектов по статусам;
- переходы из виджетов в существующие разделы ЛК.

После согласования можно расширить:

- аналитикой по агентам;
- сравнением периодов;
- финансовыми графиками;
- экспортом;
- персональными настройками отображения.
