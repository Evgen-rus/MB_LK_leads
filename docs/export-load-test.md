# Нагрузочный тест экспорта `/leads/export` (`EXPORT_MAX_ROWS`)

Короткая инструкция для проверки, можно ли повышать `EXPORT_MAX_ROWS` без риска для сервера.

## Цель

Понять безопасный лимит строк при выгрузке (особенно `XLSX`) на текущем сервере.

## Перед стартом

1. В таблице `provider_leads` должны быть реальные данные (не `rows=0`).
2. Backend должен быть запущен с текущим значением `EXPORT_MAX_ROWS`.
3. Подготовь 2 параллельных пользователя/сессии (два браузера или обычный + инкогнито).

## Быстрый сценарий (5-10 минут)

1. Установи тестовый лимит, например:
   - `EXPORT_MAX_ROWS=25000`
2. Перезапусти backend.
3. В двух сессиях одновременно открой выгрузку `XLSX` за период, где точно много лидов.
4. Повтори параллельную выгрузку 3 раза подряд.
5. Отсмотри логи и время ответов.

## Как смотреть лог

### Linux

```bash
tail -n 300 logs/app.log | grep -E "export_leads_done|export_leads_failed"
```

### PowerShell (Windows)

```powershell
Select-String -Path logs/app.log -Pattern "export_leads_done|export_leads_failed" | Select-Object -Last 100
```

## Что считать нормой

1. Нет строк `export_leads_failed`.
2. Есть строки `export_leads_done format=xlsx rows=...`.
3. `rows` в логах не нулевые.
4. Время `ms` не растет лавинообразно при параллельных запусках.

## Шкала принятия решения

1. Если 3 раунда прошли без ошибок и время приемлемое: повышай на `+5000`.
2. Если есть ошибки/сильные тормоза: откат на `-5000`.
3. Для текущего сервера (`2 GB RAM`, частые `XLSX`, параллельные выгрузки) практический потолок: около `30000`.

## Рекомендуемая лестница лимитов

1. `15000` -> `20000`
2. `20000` -> `25000`
3. `25000` -> `30000` (верхняя граница для этого сервера)

## Быстрый откат

1. Верни предыдущее стабильное значение в `.env`.
2. Перезапусти backend.
3. Повтори 1 раунд теста для проверки стабилизации.
