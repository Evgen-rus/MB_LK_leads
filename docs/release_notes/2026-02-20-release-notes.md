# Release Notes — 20.02.2026

## Кратко

- Исправлен аудит изменений при имперсонации: действия админа в ЛК клиента больше не записываются как действия клиента.
- Для событий аудита разделены:
  - владелец контекста клиента (`user_id`);
  - фактический исполнитель действия (`actor_user_id`).
- Добавлен признак выполнения через имперсонацию: `via_impersonation`.
- Обновлено отображение в историях:
  - «История изменений проекта» в клиентском ЛК;
  - «История действий клиента»;
  - админские списки изменений/истории.
- Для админа добавлена явная метка `через имперсонацию`.

## Где работает

- Backend API (аудит и формирование истории):
  - клиентские endpoints изменений проектов и ЧС;
  - админские endpoints просмотра истории и списков изменений.
- Frontend:
  - клиентская модалка истории проекта;
  - клиентская лента истории действий;
  - админские экраны истории/изменений по клиенту и ЧС.

## Что изменено

### Backend

- В `audit_events` добавлены поля:
  - `actor_user_id` — кто реально выполнил действие;
  - `via_impersonation` — признак действия админа через ЛК клиента.
- Добавлена совместимость для существующих БД:
  - при старте backend недостающие колонки добавляются автоматически.
- Токен имперсонации дополнен claim `impersonator_user_id`.
- В обработке auth выделен контекст актора для аудита:
  - при имперсонации actor = админ, subject/client = клиент.
- Логирование `AuditEvent` обновлено для project/blacklist-операций:
  - сохраняется клиентская привязка события;
  - исполнитель фиксируется как админ при имперсонации.
- В выдаче историй actor берётся из `actor_user_id` (fallback на старый `user_id`).

### Frontend

- В клиентской истории проекта добавлена колонка «Кто».
- В админских историях/списках изменений:
  - показывается фактический исполнитель;
  - для имперсонации отображается метка `через имперсонацию`.

## Совместимость и данные

- Старые записи аудита остаются валидными:
  - если `actor_user_id` отсутствует, используется fallback на старое поле;
  - в UI для части старых записей может быть прочерк в данных актора.
- Сводки и фильтры по клиентам сохраняют прежнюю бизнес-логику:
  - события по-прежнему остаются в контуре соответствующего клиента.
