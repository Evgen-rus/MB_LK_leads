# Release Notes — 09.04.2026

## Кратко

- В системе действует трёхуровневая модель ролей: `admin`, `agent`, `client`.
- Добавлен отдельный manager-контур для агентов: создание, редактирование, включение/отключение, суммарный остаток их клиентов и список этих клиентов.
- Клиента можно закреплять за агентом и переводить между админом и агентами.
- Агент работает только в рамках своих клиентов: проекты, идентификации, отчёты, чёрный список и read-only просмотр тарифов.
- Баланс клиента меняется через тарифные операции администратора и через фактический расход идентификаций по проектам; прямые ручные операции клиентского баланса отключены.
- В клиентский тариф добавлены 3 обязательных сигнала остатка: `Сигнал 1`, `Сигнал 2`, `Сигнал 3`.
- Сигналы настраиваются и при создании тарифа, и при редактировании существующего тарифа.
- Когда остаток клиента достигает порога сигнала или уходит ниже него, в Telegram отправляется уведомление.
- Проверка сигналов встроена в существующий периодический цикл лимит-контроля и не нагружает webhook-путь на каждый новый лид.
- При отключении агента его вход блокируется, проекты его клиентов ставятся на паузу, а редактирование проектов клиентами блокируется; при повторном включении автоматически в `Активен` проекты не переводятся.

## Что изменено

### Backend

- В модель `users` добавлены и используются поля для agent layer:
  - `display_name`
  - `role`
  - `owner_agent_id`
  - `is_disabled`
- JWT и `/me` возвращают роль пользователя.
- Добавлены server-side проверки manager-доступа:
  - `admin` видит всех клиентов и всех агентов;
  - `agent` видит только своих клиентов.
- Добавлены и используются endpoints для agent layer:
  - `GET /admin/agents`
  - `POST /admin/agents`
  - `PATCH /admin/agents/{agent_id}`
  - `GET /admin/agents/{agent_id}/balance`
  - `GET /admin/agents/{agent_id}/balance/ops`
  - `POST /admin/clients/{client_id}/owner`
- В manager-зоне `/admin/users`, `/admin/projects`, `/admin/leads`, `/admin/blacklist`, `/admin/reports`, `/admin/changes/*`, `/admin/clients/summary`, `/admin/clients/{client_id}/balance*`, `/admin/clients/{client_id}/tariffs*`, `/admin/tariffs/{tariff_id}*` добавлены role-aware ограничения по доступным клиентам.
- Агентский баланс переосмыслен:
  - отдельный долг/баланс агента больше не является основной метрикой;
  - баланс агента считается как сумма текущих `remaining` всех его клиентов;
  - при смене владельца клиента баланс агента пересчитывается через `owner_agent_id`, без переноса остатка клиента в отдельные balance-операции агента.
- Прямые операции баланса клиента и агента отключены:
  - клиентский баланс изменяется через тарифные операции;
  - прямое ручное изменение агентского баланса не используется.
- Тарифный контур клиента изменён:
  - тариф можно назначать только клиенту;
  - создание тарифа и `credit` / `debit` внутри тарифа автоматически создают зеркальную запись в `ClientBalanceOperation`;
  - поэтому тарифы влияют на `remaining`, лимит-контроль и автопаузу;
  - менять тарифы может только админ;
  - агенту доступен только read-only просмотр тарифов и их истории у своих клиентов.
- В модель `client_tariffs` добавлены поля:
  - `signal1`
  - `signal2`
  - `signal3`
- В модель `users` добавлено поле:
  - `telegram_tariff_signal_level`
- Добавлена server-side валидация сигналов тарифа:
  - все 3 поля обязательны;
  - `signal1 > signal2 > signal3 > 0`;
  - `signal1 < текущий размер тарифа`.
- Создание тарифа обновлено:
  - без сигналов тариф создать нельзя;
  - сигналы сохраняются вместе с тарифом.
- Добавлен `PATCH /admin/tariffs/{tariff_id}`:
  - позволяет менять текущий размер тарифа;
  - позволяет менять `signal1` / `signal2` / `signal3`;
  - изменение тарифа по сумме по-прежнему зеркалится в `ClientBalanceOperation`.
- Логика тарифных операций усилена:
  - backend не даст увести тариф ниже его сигналов через корректировки.
- В периодический лимит-контроль добавлена проверка тарифных сигналов:
  - берётся текущий `remaining` клиента;
  - берётся последний созданный тариф клиента;
  - определяется, достигнут ли новый сигнал;
  - если да, отправляется Telegram-сообщение и фиксируется уровень отправленного сигнала.
- Поведение при ошибке Telegram для тарифных сигналов:
  - цикл не падает;
  - сигнал не помечается как отправленный;
  - на следующем проходе будет повторная попытка.
- Исправлена маршрутизация клиентских Telegram-уведомлений в фоне:
  - если у клиента включён персональный Telegram-маршрут и задан `chat_id`, уведомление уходит в него;
  - иначе используется общий `TELEGRAM_CHAT_ID`.
- При отключении агента backend:
  - запрещает вход агенту;
  - ставит проекты его клиентов на паузу;
  - включает клиентам `projects_mutation_locked` с причиной `Агент отключён администратором`.
- При повторном включении агента backend:
  - снимает `projects_mutation_locked` у его клиентов только если блокировка была поставлена именно из-за отключения агента;
  - не переводит проекты автоматически в `Активен`.

### Frontend

- В приложение добавлена роль `agent` в навигации и bootstrap-логике JWT.
- Добавлен экран `Агенты` для администратора:
  - список агентов;
  - создание и редактирование агента;
  - включение/отключение;
  - суммарный остаток клиентов агента;
  - список закреплённых клиентов.
- Экран `Клиенты` обновлён:
  - отображается владелец клиента (`admin` / конкретный агент);
  - админ может переназначать клиента между админом и агентами;
  - агент видит только своих клиентов;
  - агенту скрыты действия, не соответствующие backend-правам.
- Экран `Баланс` обновлён:
  - прямые кнопки `Начислить номера` / `Списать номера` для клиента убраны;
  - управление тарифами вынесено в popup;
  - админ управляет тарифами клиента через popup;
  - агент может открыть только read-only просмотр тарифов и истории тарифов своих клиентов.
- Карточки создания и редактирования клиента адаптированы под роль агента:
  - скрыты админские поля и действия, которые агент не должен использовать;
  - агент видит и использует только действия, разрешённые backend-правами.
- Manager-режим для проектов, лидов, отчётов и чёрного списка приведён к единому поведению для `admin` и `agent` с серверными ограничениями по клиентам.
- Popup управления тарифами дополнительно обновлён:
  - при создании тарифа появились обязательные поля `Сигнал 1`, `Сигнал 2`, `Сигнал 3`;
  - при редактировании тарифа сигналы тоже можно менять;
  - добавлена UI-валидация порядка сигналов и связи с размером тарифа.
- В таблице тарифов и в сводке выбранного тарифа показываются значения сигналов.
- Front API-контракт расширен:
  - создание тарифа теперь отправляет сигналы;
  - редактирование тарифа переведено на отдельный `PATCH` endpoint.

## Поведение системы

- `admin`, `agent` и `client` являются разными ролями на backend и frontend.
- Клиент может быть:
  - прямым клиентом админа;
  - клиентом конкретного агента.
- Баланс агента считается как сумма текущих остатков его клиентов, а не как отдельный долг/баланс самого агента.
- Тарифы меняют баланс клиента через зеркальные записи в `ClientBalanceOperation`, поэтому влияют на `remaining`, лимит-контроль и автопаузу.
- Агент не управляет балансом клиентов и не меняет их тарифы в ЛК.
- Автоматическое возобновление проектов после повторного включения агента не выполняется.
- Сигналы проверяются не в момент записи каждого нового лида, а в рамках существующего периодического фонового цикла.
- Это означает:
  - остаток клиента учитывает фактический расход идентификаций как и раньше;
  - Telegram-сигнал может прийти с задержкой до следующего прохода фонового цикла.
- Если остаток клиента:
  - стал меньше или равен `signal1` -> отправляется уведомление по сигналу 1;
  - стал меньше или равен `signal2` -> отправляется уведомление по сигналу 2;
  - стал меньше или равен `signal3` -> отправляется уведомление по сигналу 3.
- Если остаток пересёк сразу несколько сигналов за один проход, отправляется одно сообщение только по самому нижнему достигнутому сигналу.
- Если остаток позже восстановился выше порога, а потом снова опустился ниже него, сигнал может быть отправлен повторно.

## Зачем это нужно

- Даёт отдельный рабочий контур для агентского уровня без смешивания его с клиентским ЛК и без потери полного контроля у администратора.
- Позволяет делегировать агентам работу с клиентами, проектами и отчётностью, сохраняя изменение тарифов и баланса под контролем администратора.
- Формализует ownership клиента и даёт администратору сводный финансовый показатель по текущему клиентскому портфелю агента.
- Даёт администратору управляемые точки предупреждения по остатку клиента без привязки к расчётным "дням до нуля".
- Позволяет заранее уведомлять о снижении остатка на бизнес-порогах, которые понятны менеджеру и клиенту.
- Сохраняет текущую архитектурную модель без лишней нагрузки на webhook, БД и CPU: проверка встроена в уже существующий фоновый цикл.
- Удерживает критичные ограничения на backend, а не только в UI.
