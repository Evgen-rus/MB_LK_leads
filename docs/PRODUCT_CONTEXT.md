# Контекст продукта: Mad Boss leads (MB_LK_leads)

> Файл собран по фронтенду (`my-app-vite`), типам/API-клиенту (`src/api.ts`), корневому `README.md` репозитория и комментариям в коде. Часть формулировок уточнена **по ответам разработчика** (см. раздел в конце про то, что всё ещё нельзя выдумывать).

Актуально на: 2026-04-07

## 1. Что это за продукт

Веб-личный кабинет (**Mad Boss leads** — так назван бренд в боковом меню) для работы с **проектами** сбора контактов, просмотра **идентификаций**, **отчётов**, **чёрного списка** телефонов и **баланса** по номерам. В продукте теперь три уровня доступа: **клиент**, **агент** и **администратор**. У администратора есть полный контур управления клиентами, агентами, балансами, тарифами и импортом лидов из XLSX. У агента — manager-режим только в рамках своих клиентов.

**Идентификации** (в коде и API часто «лиды» / `leads`) — по смыслу это **те же сырые лиды**, что приходят от поставщика, но **привязанные к конкретному проекту** (запись без привязки к проекту в интерфейсе отображается без проекта).

После входа клиент по умолчанию попадает в раздел «Идентификации», агент и администратор — в раздел «Клиенты».

## 2. Технология (кратко)

Одностраничное веб-приложение: **React 19 + TypeScript + Vite**; общение с **REST API** (Bearer JWT в `localStorage`, для скачивания файлов — cookie). Бэкенд в этом же репозитории — **FastAPI** (см. `README.md`). Прод-домен фронта в коде упоминается как `leadrecordwh.ru` (проксирование API через `/api`).

## 3. Роли и доступ

- **Клиент** — обычный пользователь после логина; видит свои проекты, идентификации, отчёты, баланс, чёрный список, техподдержку, интеграции; раздел **«История изменений»** (активность) доступен **только** клиенту, не админу (для админа показывается явное сообщение об ограничении).
- **Агент** — отдельный manager-уровень. Входит в тот же `/admin/*` контур, но видит **только своих клиентов**. Может работать с проектами, идентификациями, отчётами и чёрным списком **только своих клиентов**, а также смотреть тарифы и историю тарифов своих клиентов в режиме read-only. Агент **не** управляет агентами, **не** видит чужих клиентов, **не** меняет баланс клиентов и **не** создаёт/не редактирует тарифы клиентов.
- **Администратор** — на бэкенде при выдаче токена: **`is_admin = true` только если `user.id == 1`** (`backend/app/main.py`, эндпоинт логина). В JWT попадает то же значение; **других админов по этому правилу нет**. При **имперсонации** выдаётся токен **без** флага админа (от имени клиента).

Возможности админа (по UI и API): список **клиентов** с агрегатами, список **агентов**, создание/редактирование агентов, перевод клиента между админом и агентами, **проекты всех клиентов**, **имперсонация** (вход «от имени» клиента через отдельный запрос), **очередь изменений** клиентов, **пауза/возобновление сбора** по клиенту, просмотр **баланса** клиента и **баланса агента**, новый **тарифный контур** клиента (создание тарифа и корректировки внутри тарифа, которые меняют баланс клиента), админские **идентификации**, **чёрный список**, **отчёты**, **импорт лидов из XLSX** (только админ, на бэкенде — проверка прав администратора), история проекта с фильтрами **pending/done**.

Важное правило по владению клиентом:

- клиент может быть либо прямым клиентом админа, либо клиентом конкретного агента;
- при переводе клиента агенту его текущий старый остаток становится долгом агента;
- агент может уходить в минус;
- минус агента сам по себе не ставит проекты клиентов на паузу автоматически.

**Пауза клиента (ответ разработчика):** админ может поставить клиента на паузу — **все включённые проекты** переходят в паузу, **клиент не может редактировать проекты** (блокировка правок со стороны админки).

**Отключение агента:** админ может отключить агента. В этом состоянии агент не может войти, активные проекты его клиентов ставятся на паузу, а клиентам агента блокируется редактирование проектов. При повторном включении агента вход снова разрешён, блокировка редактирования у его клиентов снимается, но проекты автоматически не переводятся обратно в `Активен`.

**Авто-контроль лимитов (ответ разработчика):** если опция включена, при превышении суммы лимитов **активных** проектов над **остатком** система **отключает проекты**, начиная с **наибольшего лимита**, пока сумма не согласуется с остатком. Текущая реализация в бэкенде выполняет эту проверку **периодическим фоновым циклом**, а не запускает её на каждый новый лид внутри webhook-запроса.

**Telegram-уведомления (ответ разработчика + подписи в ЛК):** уведомления по **остатку** уходят в **Telegram-группу клиента**, если назначены **chat ID** и включено «Использовать этот чат для уведомлений»; **технические** уведомления и сценарий, когда группа не настроена — в **общий чат админа** (значение по умолчанию из настроек сервера / env). В коде бэкенда маршрут в группу клиента завязан на поле пользователя `telegram_auto_pause_enabled` (в интерфейсе админки названо про уведомления, не про отдельную «автопаузу»).

У клиента на уровне профиля (`/me`) также бывают: **блокировка изменения проектов** (`projectsMutationLocked`), **уникальные имена новых проектов** — см. код и сценарии в `README.md`.

## 5. Сущности и связи (бизнес-языком)

- **Клиент (пользователь ЛК)** — учётная запись с логином, отображаемым именем, профилем (в админке: название, ИНН, телефон, контакт). Может быть прямым клиентом админа или клиентом конкретного агента. Связан с **проектами**, **балансом**, **тарифами**, **чёрным списком**, **отчётами**.
- **Агент** — отдельная учётная запись manager-уровня без клиентского ЛК. У агента есть собственный старый баланс, список закреплённых клиентов и отдельный флаг отключения. Агент работает только в рамках своих клиентов и не управляет их балансом или тарифами.
- **Проект** — единица настройки сбора: **название**, **тег**, **статус проекта** (Активен / На паузе / Удалён), **лимит** и **баланс** в бизнес-смысле считаются в **штуках идентификаций** (по сути **номеров телефонов**), **источник сбора** (Сайты, Звонки, СМС, Ретросайты, Ретрозвонки, Пересечение), **код источника данных B1–B4** — для заказчика это **код канала/источника в его контексте** (дополнительной «человеческой» расшифровки в ТЗ не требуется), **регионы** (режим включить/исключить), **сайты и/или телефоны** конкурентов (в зависимости от типа источника), **имя отправителя SMS** (для СМС), **дни получения** (дни недели). У проекта считаются **номера за период**, **всего**, **доменов/номеров** (количество источников). У клиента в таблице проектов отображаются не все поля админки.
- **Статус отгрузки** в модели/UI (Активна / На модерации / Отключена) — **легаси**; **«На модерации» по процессу не используется**. В рабочем процессе важны **Активен** и **На паузе** у **проекта**: в **Активен** у поставщика проект **включается по API**, **идентификации приходят на вебхук**; **На паузе** — соответственно выключено/не отгружается. Поле `deliveryStatus` в данных может сохраняться для совместимости — не путать с актуальным процессом без сверки с бэкендом.
- **Идентификация** — запись с **датой** (в таблице по умолчанию показывается время попадания в БД), **проектом** (или «—» если не привязано), **каналом** (например B1…B4), **источником** (в UI колонка совпадает с UTM-кампанией из API), **телефоном**. Сырые лиды с вебхука после привязки к проекту попадают сюда же. Внутренний идентификатор в API — `ext_id`.
- **Отчёт** — заявка на выгрузку за период с выбором проектов и формата (CSV/XLSX); в списке — дата создания, период, формат; скачивание через связанный экспорт.
- **Чёрный список** — номера телефонов, дата добавления; у админа виден ещё и клиент.
- **Баланс** — контур операций **начисление (credit)** и **списание (debit)** с суммой и комментарием; сводка: начислено, списано, баланс, использовано, остаток, признак долга, период. Для клиента этот контур участвует в расчёте остатка и лимит-контроля; новые записи баланса теперь могут появляться как следствие тарифных операций админа. Этот же контур используется и для баланса агента.
- **Тариф** — клиентский тарифный контур: каждый тариф создаётся как отдельная запись, внутри конкретного тарифа можно делать добавления и списания с комментарием. Тарифные операции автоматически меняют баланс клиента, а значит влияют на `remaining`, лимит-контроль и автопаузу. Как «текущий тариф» показывается **последний созданный тариф** с учётом его внутренних корректировок. Изменять тарифы может только админ; агенту доступен только просмотр тарифов своих клиентов.
- **Изменения (админ)** — очередь действий клиента (создание/изменение/удаление проекта, добавление/удаление в ЧС) со статусами **ожидает / выполнено**, снимки «до/после», пакетные создания.
- **История проекта** — события create/update/delete с описанием и режимом актора (клиент, админ, имперсонация).
- **История активности (клиент)** — события по сущностям **проект**, **чёрный список**, **баланс**, **отчёт** с текстовым описанием.

На экране **Клиенты (админ)** у строки выводится вычисляемый **статус строки**: Активен / Нет проектов / Долг / Дожим (логика на фронте: нет проектов, остаток ≤ 0, остаток < 15% от лимита и т.д.).

## 6. Типовые сценарии (по коду)

1. **Вход** — логин/пароль → JWT → редирект на основной экран; выход очищает токен и cookie.
2. **Клиент: работа с проектами** — поиск по названию/ID, фильтр по статусу, календарь периода для метрик, пагинация; создание проекта (модалка); редактирование; просмотр **истории изменений** проекта; переход к **идентификациям** за выбранный период или «за всё время»; удаление проекта; переключение Активен ↔ На паузе; **массовые правки**: дни получения, лимит, телефоны/сайты, регионы, статус. Если админ включил блокировку — создание/редактирование недоступны (тост). Для проектов с источником **СМС** редактирование и смена статуса в ЛК разрешены, но применяются только локально в нашей системе без запроса к провайдеру; это же правило действует для автопаузы по лимитам и admin collection pause/resume. Удаление остаётся обычным провайдерским сценарием.
3. **Клиент: идентификации** — фильтр проектов и «каналов», период дат, экспорт; переход из таблицы проектов с предзаполненными фильтрами.
4. **Клиент: отчёты** — сформировать отчёт за период, скачать из списка.
5. **Клиент: баланс** — просмотр сводки и списка операций за период.
6. **Клиент: чёрный список** — поиск, добавление номеров, удаление записи.
7. **Клиент: поддержка / интеграции** — отправка сообщения на бэкенд (`/support-message`) с телефоном и текстом.
8. **Клиент: история** — лента событий с фильтрами по дате, сущности, поиску.
9. **Manager: клиенты** — обзор по периоду, создание клиента, редактирование карточки, переход к проектам / очереди изменений / событиям ЧС / балансу; у админа дополнительно есть пауза/возобновление **сбора** по клиенту, имперсонация и перевод клиента между админом и агентами; у агента — только свои клиенты.
10. **Админ: агенты** — создание/редактирование агента, включение/отключение, просмотр баланса агента и истории операций, список закреплённых клиентов.
11. **Manager: проекты** — фильтрация по клиенту, массовые действия, редактирование полей проекта (в т.ч. легаси-поля **статуса отгрузки** в данных), переход к идентификациям клиента и к чёрному списку клиента; агент работает только с проектами своих клиентов.
12. **Manager: очередь изменений** — просмотр и **подтверждение (resolve)** записей в рамках доступных клиентов.
13. **Manager: баланс** — просмотр баланса клиента и тарифов; прямые ручные операции баланса клиента отключены, а изменение клиентского баланса выполняется через тарифные операции админа. В этом же сценарии админ создаёт тарифы, смотрит список тарифов клиента и делает добавления/списания внутри конкретного тарифа. Агент может только смотреть тарифы и их историю у своих клиентов.
14. **Админ: импорт лидов из XLSX** — выбор файла, **preview** (количество строк, валидные, уже существующие дубли в БД, готовые к импорту, проблемы с проектами); **импорт** только после успешного preview и только если нет строк без однозначного проекта и без неоднозначного совпадения проекта; перед записью данные снова валидируются на сервере, дедупликация по `vid`. Служебный **CLI**-скрипт в репозитории остаётся резервным вариантом (см. §7).

## 7. Интеграции и внешние системы

По **`README.md` репозитория** (не только по UI):

- **Prostats** — внешний API для операций с проектами (`PROSTATS_TOKEN` и др.); при создании проекта возможно несколько технических проектов на разные коды B1–B4; есть сценарий **уникальных имён** с переименованием в Prostats.
- **Telegram** — уведомления (остаток, автопауза по лимитам, техсобытия) и доставка обращений из поддержки; маршрут в чат клиента vs общий админский — см. §3.
- **Google Sheets** — экспорт (отдельный скрипт в репо, не экран ЛК).
- **Вебхук провайдера** — приём лидов на backend (`POST /api/provider-test/{secret}`), связь с проектом по имени страницы и правилам из README. В текущей архитектуре webhook старается **быстро принять и сохранить лид**, а лимит-контроль выполняется отдельно по интервалу.
- **Импорт лидов из XLSX (админский ЛК)** — восстановление или догрузка идентификаций из файла провайдера **без SSH**: двухшаговый API (preview → commit по временной сессии), общая бизнес-логика с вебхуком там, где это задумано (в т.ч. разбор `prov_chanel` / `prov_source` от имени проекта). **Резерв:** скрипт `tool_import_provider_leads_from_xlsx.py` для ручного запуска с сервера.

Экран **Интеграции** — маркетинговый текст и сценарий «написать в поддержку». **Автоматической интеграции с CRM в ЛК нет**; всё, что выходит за рамки ручной настройки командой, **не заявлено** (ответ разработчика: нет).

## 8. Ограничения и неочевидное

- **Маршрутизация SPA:** почти все разделы без отдельного URL — при обновлении страницы откроется последнее сохранённое в `localStorage` представление (кроме логина).
- **Дубликаты доменов/номеров** между проектами — бэкенд возвращает структурированную ошибку; фронт показывает список конфликтов.
- **Авто-контроль лимитов** — при несоответствии суммы лимитов активных проектов и остатка бэкенд **отключает проекты с наибольшего лимита**; при включении проекта клиентом фронт может показать отказ с текстом про сумму лимитов и остаток.
- **Тарифы и баланс** — это два связанных контура: тарифные операции зеркалятся в баланс клиента, поэтому меняют `remaining`, участвуют в лимит-контроле и могут влиять на автопаузу.
- **Агентский уровень** — это не отдельный продукт, а manager-режим поверх тех же `/admin/*`; ограничения агента обязательно проверяются на backend, а не только скрываются в UI.
- **Отключение агента** — это два разных эффекта: запрет входа самому агенту и блокировка редактирования проектов у его клиентов. При повторном включении агента блокировка редактирования снимается, но сами проекты автоматически не активируются.
- Разделы **Обучение** и **Онбординг** — только заглушки в UI; **наполнение и сроки отложены** (ответ разработчика).
- Кнопка **WhatsApp** на экране техподдержки ведёт на **тот же URL, что и Telegram** — **намеренная заглушка**, отдельной ссылки на WhatsApp пока нет.
- **Импорт лидов (админ):** запись в БД возможна только после **preview** и отдельного подтверждения; если в сводке есть необработанные проекты (`notFoundProjects`) или неоднозначные совпадения (`ambiguousProjects`), кнопка импорта недоступна до исправления файла.

## 9. Глоссарий

| Как в UI (предпочтительно) | Альтернативные названия в коде/API |
|----------------------------|-----------------------------------|
| Идентификации | лиды, `leads`, таблица `Lead` |
| Проект | `Project`, `/projects` |
| Статус проекта | Активен / На паузе / Удалён |
| Статус отгрузки | Активна / На модерации / Отключена (`deliveryStatus`, **легаси**; в процессе опираться на статус проекта) |
| Источник сбора | Сайты, Звонки, СМС, … (`collectionSource`) |
| Канал (в таблице идентификаций) | код B1–B4, поле `source` |
| Источник (колонка в идентификациях) | в API часто `utm_campaign` |
| Лимит | `dataLimit` (в штуках идентификаций / номеров) |
| Доменов/номеров | количество источников сбора (`sourcesCount`) |
| Чёрный список | `blacklist` |
| Клиент (в админке) | пользователь `UserInfo`, `clientId` |
| Агент | отдельный `UserInfo` с `role = agent`, владелец клиентов |
| Начисление / списание (баланс) | `credit` / `debit` |
| Тариф | `ClientTariff`, клиентский тарифный контур, который зеркалит изменения в баланс клиента |
| Очередь изменений | `admin/changes`, статусы pending/done |
| Импорт лидов (админ) | XLSX, эндпоинты `admin/provider-leads-import` (preview / commit), временная сессия по `previewId` |
