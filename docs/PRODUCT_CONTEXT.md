# Контекст продукта: Mad Boss leads (MB_LK_leads)

> Файл собран по `ARCHITECTURE.md`, фронтенду (`my-app-vite`), типам/API-клиенту (`src/api.ts`), корневому `README.md` репозитория, release notes и комментариям в коде. Если этот документ расходится с кодом или `ARCHITECTURE.md`, источником истины остаётся код.

Актуально на: 2026-06-15

## 1. Что это за продукт

Веб-личный кабинет (**Mad Boss leads** — так назван бренд в боковом меню) для работы с **проектами** сбора контактов, просмотра **идентификаций**, **отчётов**, **чёрного списка** телефонов и **баланса** по номерам. В продукте три уровня доступа: **клиент**, **агент** и **администратор**. У клиента есть обзорный дашборд по своим проектам, идентификациям и остатку. У администратора есть управленческий **дашборд**, полный контур управления клиентами, агентами, тарифами, импортом лидов из XLSX и служебными проверками. У агента — manager-режим только в рамках своих клиентов.

**Идентификации** (в коде и API часто «лиды» / `leads`) — по смыслу это **те же сырые лиды**, что приходят от поставщика или Пикселя, но **привязанные к конкретному проекту** (запись без привязки к проекту в интерфейсе отображается без проекта).

После входа клиент по умолчанию попадает в раздел «Дашборд», агент — в раздел «Клиенты», администратор — в раздел «Дашборд».

## 2. Технология (кратко)

Одностраничное веб-приложение: **React 19 + TypeScript + Vite**; общение с **REST API** (Bearer JWT в `localStorage`, для скачивания файлов — cookie). Бэкенд в этом же репозитории — **FastAPI** (см. `README.md`). Прод-домен фронта в коде упоминается как `leadrecordwh.ru` (проксирование API через `/api`).

## 3. Роли и доступ

- **Клиент** — обычный пользователь после логина; видит свой дашборд, проекты, идентификации, отчёты, баланс, чёрный список, техподдержку, интеграции. История изменений доступна через колокольчик и ленту активности клиента.
- **Агент** — отдельный manager-уровень. Входит в тот же `/admin/*` контур, но видит **только своих клиентов**. Может работать с проектами, идентификациями, отчётами и чёрным списком **только своих клиентов**, а также смотреть тарифы и историю тарифов своих клиентов в режиме read-only. Агент **не** управляет агентами, **не** видит чужих клиентов, **не** меняет баланс клиентов и **не** создаёт/не редактирует тарифы клиентов.
- **Администратор** — на бэкенде при выдаче токена: **`is_admin = true` только если `user.id == 1`** (`backend/app/main.py`, эндпоинт логина). В JWT попадает то же значение; **других админов по этому правилу нет**. При **имперсонации** выдаётся токен **без** флага админа (от имени клиента).

Возможности админа (по UI и API): управленческий **дашборд** с KPI, рисками, графиками и рейтингами, список **клиентов** с агрегатами, список **агентов**, создание/редактирование агентов, перевод клиента между админом и агентами, **проекты всех клиентов**, **имперсонация** (вход «от имени» клиента или агента через отдельный запрос), **очередь изменений** клиентов, **пауза/возобновление сбора** по клиенту, просмотр **баланса** клиента и агрегированного остатка клиентов агента, **тарифный контур** клиента (создание тарифа и корректировки внутри тарифа, которые меняют баланс клиента), админские **идентификации**, **чёрный список**, **отчёты**, **общая история изменений**, **импорт лидов из XLSX** (только админ, на бэкенде — проверка прав администратора), история проекта с фильтрами **pending/done**, ручной запуск проверки блокировок `B4`.

Важное правило по владению клиентом:

- клиент может быть либо прямым клиентом админа, либо клиентом конкретного агента;
- агентский баланс больше не является отдельным учётным контуром;
- в интерфейсе агента показывается агрегат: сумма текущих `remaining` всех клиентов, закреплённых за агентом;
- при переводе клиента между админом и агентом остаток клиента не переносится отдельной balance-операцией агента.

**Пауза клиента (ответ разработчика):** админ может поставить клиента на паузу — **все включённые проекты** переходят в паузу, **клиент не может редактировать проекты** (блокировка правок со стороны админки).

**Отключение агента:** админ может отключить агента. В этом состоянии агент не может войти, активные проекты его клиентов ставятся на паузу, а клиентам агента блокируется редактирование проектов. При повторном включении агента вход снова разрешён, блокировка редактирования у его клиентов снимается, но проекты автоматически не переводятся обратно в `Активен`.

**Авто-контроль лимитов (ответ разработчика):** если опция включена, при превышении суммы лимитов **активных** проектов над **остатком** система **отключает проекты**, начиная с **наибольшего лимита**, пока сумма не согласуется с остатком. Текущая реализация в бэкенде выполняет эту проверку **периодическим фоновым циклом**, а не запускает её на каждый новый лид внутри webhook-запроса.

**Telegram-уведомления:** backend кладёт сообщения в `telegram_notifications`, а внешний `telegram_worker.py` отправляет их через Telegram Bot API. Уведомления по тарифным сигналам, успешному созданию тарифа, доначислению и списанию уходят в **Telegram-группу клиента**, если назначен **chat ID** и включено «Использовать этот чат для уведомлений»; если группа не настроена, используется **общий чат админа** (`TELEGRAM_CHAT_ID`). Для сигналов остатка в общем чате используется технический формат. В персональных сигналах прогноза остатка средний расход считается за последние 7 суток с округлением количества дней вниз. Автопауза по лимитам, B4-блокировки, пустой ответ поставщика при B4-проверке и достижение 100% дневного лимита проекта являются техническими событиями и всегда уходят в общий чат админа. Для успешного создания и изменения `СМС`-проекта дополнительно ставится outbox-уведомление в общий чат.

У клиента на уровне профиля (`/me`) также бывают: **блокировка изменения проектов** (`projectsMutationLocked`), **уникальные имена новых проектов** — см. код и сценарии в `README.md`.

## 5. Сущности и связи (бизнес-языком)

- **Клиент (пользователь ЛК)** — учётная запись с логином, отображаемым именем, профилем (в админке: название, ИНН, телефон, контакт, внутренний идентификатор клиента, ссылка на таблицу, ручной рабочий статус). Может быть прямым клиентом админа или клиентом конкретного агента. Связан с **проектами**, **балансом**, **тарифами**, **чёрным списком**, **отчётами**.
- **Агент** — отдельная учётная запись manager-уровня без клиентского контура. У агента есть список закреплённых клиентов и отдельный флаг отключения. Отдельный баланс агента не ведётся: показатель в UI считается как сумма `remaining` его клиентов. Агент работает только в рамках своих клиентов и не управляет их балансом или тарифами.
- **Проект** — единица настройки сбора: **название**, **тег**, **статус проекта** (Активен / На паузе / Удалён / системная Блокировка оператора), **дневной лимит проекта** (`dataLimit`) и **баланс клиента** в бизнес-смысле считаются в **штуках идентификаций** (по сути **номеров телефонов**), **источник сбора** (Сайты, Звонки, СМС, Ретросайты, Ретрозвонки, Пересечение, Пиксель), **код источника данных B1–B4** — raw-код интеграций; во frontend он отображается пользователю как A/B/C/D, **регионы** (режим включить/исключить), **сайты и/или телефоны** конкурентов (в зависимости от типа источника), **имя отправителя SMS** (для СМС), **дни получения** (дни недели). У проекта считаются **номера за период**, **всего**, **доменов/номеров** (количество источников). У клиента в таблице проектов отображаются не все поля админки. Для Пикселя один проект соответствует одному домену сайта: название проекта и домен совпадают, канал A/B/C/D не используется.
- **Пиксель-проект** — локальный проект с источником сбора **Пиксель**. Он не создаётся в Prostats, не имеет канала A/B/C/D, хранит домен сайта клиента и после создания не позволяет менять название/домен. Для нового домена создаётся новый Пиксель-проект.
- **Статус отгрузки** в модели/UI (Активна / На модерации / Отключена) — **легаси**; **«На модерации» по процессу не используется**. В рабочем процессе важны **Активен** и **На паузе** у **проекта**: в **Активен** у поставщика проект **включается по API**, **идентификации приходят на вебхук**; **На паузе** — соответственно выключено/не отгружается. Поле `deliveryStatus` в данных может сохраняться для совместимости — не путать с актуальным процессом без сверки с бэкендом.
- **Идентификация** — запись с **датой** (в таблице по умолчанию показывается время попадания в БД), **проектом** (или «—» если не привязано), **источником сбора**, **каналом** (например B1…B4 в API и A…D в UI; для Пикселя показывается `—`), **источником** (для provider — UTM-кампания из API, для Пикселя — `pixel_url`), **телефоном** и публичным **`lk id`**. Сырые лиды с вебхука после привязки к проекту попадают сюда же. Provider `vid` в API остаётся `ext_id`; `lk id` вычисляется как `30100000 + provider_leads.id` и отдельной колонкой в БД не хранится.
- **Отчёт** — заявка на выгрузку за период с выбором проектов и формата (CSV/XLSX); в списке — дата создания, период, формат; скачивание через связанный экспорт.
- **Чёрный список** — номера телефонов, дата добавления; у админа виден ещё и клиент.
- **Баланс** — контур операций **начисление (credit)** и **списание (debit)** с суммой и комментарием; сводка: начислено, списано, баланс, использовано, остаток, признак долга, период. Для клиента этот контур участвует в расчёте остатка и лимит-контроля; расход считается по привязанным идентификациям, включая Пиксель. Новые записи баланса появляются прежде всего как следствие тарифных операций админа. Баланс агента не ведётся этим контуром отдельно: он считается агрегированием остатков клиентов агента.
- **Тариф** — клиентский тарифный контур: каждый тариф создаётся как отдельная запись, внутри конкретного тарифа можно делать добавления и списания с комментарием. Тарифные операции автоматически меняют баланс клиента, а значит влияют на `remaining`, лимит-контроль и автопаузу. У тарифа обязательны `signal1 > signal2 > 0`; необязательный повторный критический `signal3` при заполнении должен соответствовать правилу `signal2 > signal3 > 0`. При этом `signal1` меньше текущего размера тарифа. Как «текущий тариф» показывается **последний созданный тариф** с учётом его внутренних корректировок. Изменять тарифы может только админ; агенту доступен только просмотр тарифов своих клиентов.
- **Дневной лимит проекта** — отдельный от баланса клиента контур. Фильтр `dailyLimitReached` и Telegram-сигнал «проект достиг 100% дневного лимита» смотрят на `count(provider_leads) >= project.data_limit` за выбранный период/день, а не на `remaining` клиента. Уведомление проверяется периодическим фоновым циклом и дедуплицируется по `daily_limit_reached_notified_limit`.
- **Админский дашборд** — обзорный экран руководителя. Он не является отдельной сущностью БД: backend собирает агрегаты из клиентов, проектов, привязанных `provider_leads`, тарифов, баланса и ошибок проектных операций. “Полученные данные” и “расход” в дашборде считаются по привязанным идентификациям (`provider_leads.project_id IS NOT NULL`), а непривязанные лиды показываются отдельно как операционный риск.
- **Клиентский дашборд** — обзорный экран клиента. Backend собирает агрегаты через `GET /dashboard`: идентификации за период/сегодня/7/30 дней, активные и заблокированные проекты, остаток и прогноз, дневной график, статусы проектов, проекты внимания и топ проектов по идентификациям.
- **Изменения (админ)** — очередь действий клиента (создание/изменение/удаление проекта, добавление/удаление в ЧС) со статусами **ожидает / выполнено**, снимки «до/после», пакетные создания. Успешные `create/update/delete` по не-`СМС` проектам стартуют как `done`; ручной review по проектам остаётся для `СМС`. Неудачные проектные операции хранятся отдельно в `project_operation_events` и в pending-очередь не попадают.
- **История проекта** — успешные и неуспешные события create/update/delete с описанием, результатом операции и режимом актора (клиент, админ, агент, имперсонация). Полная карточка изменения подгружается по клику.
- **История активности** — события по сущностям **проект**, **чёрный список**, **баланс**, **отчёт** с текстовым описанием. Есть клиентская лента и manager-лента по доступным клиентам.

В manager-таблицах клиентов нет одного общего “статуса клиента”. Вместо него используются три независимых блока: **Сбор данных** (Нет проектов / Сбор активен / На паузе), **Остаток** (число и финансовый бейдж Дожим 1/2/3 или Долг, только если у клиента есть тариф) и **Работа** (ручной статус менеджера: В работе, Ждём оплату, Ждём данные, На согласовании, Пауза по клиенту, Неактивен).

## 6. Типовые сценарии (по коду)

1. **Вход** — логин/пароль → JWT → редирект на основной экран; выход очищает токен и cookie. После успешного ввода логина/пароля клиент открывает «Дашборд», админ — «Дашборд», агент — «Клиенты»; при обычном обновлении страницы сохраняется последняя вкладка из `localStorage`.
2. **Клиент: дашборд** — обзор за период: идентификации, активные/заблокированные проекты, остаток и прогноз, дневной график, статусы проектов, проекты внимания, топ проектов; быстрые переходы ведут в идентификации, проекты, баланс и историю.
3. **Клиент: работа с проектами** — поиск по названию/ID, фильтр по статусу, фильтр достижения дневного лимита, календарь периода для метрик, пагинация; создание проекта (модалка); редактирование; просмотр **истории изменений** проекта; переход к **идентификациям** за выбранный период или «за всё время»; удаление проекта; переключение Активен ↔ На паузе; **массовые правки**: дни получения, лимит, телефоны/сайты, регионы, статус. Если админ включил блокировку — создание, изменение, переключение статуса, массовые операции и удаление недоступны, но карточку проекта можно открыть для просмотра. Для проектов с источником **СМС** редактирование и смена статуса в ЛК разрешены, но применяются только локально в нашей системе без запроса к провайдеру; это же правило действует для автопаузы по лимитам и admin collection pause/resume. Пиксель-проекты тоже локальные: один проект = один домен, без Prostats, без канала A/B/C/D; после создания домен и название не меняются. В админских бейджах `Изменения/Создания` ручной review по проектам теперь остаётся только для `СМС`: новые успешные события по обычным проектам автоматически считаются выполненными. Статус **Блокировка оператора** виден в таблицах, но не выбирается вручную; пользователь может перезапустить такой проект обычным переводом в `Активен`.
4. **Клиент: идентификации** — фильтр проектов, «каналов», источника сбора, период дат, просмотр `lk id`, экспорт; переход из таблицы проектов с предзаполненными фильтрами. Для Пикселя в таблице показывается **Источник сбора = Пиксель**, **Канал = —**, **Источники = pixel_url**.
5. **Клиент: отчёты** — сформировать отчёт за период, скачать из списка.
6. **Клиент: баланс** — просмотр сводки и списка операций за период.
7. **Клиент: чёрный список** — поиск, добавление номеров, удаление записи.
8. **Клиент: поддержка / интеграции** — отправка сообщения на бэкенд (`/support-message`) с телефоном и текстом.
9. **Клиент: история** — лента событий с фильтрами по дате, сущности, поиску.
10. **Админ: дашборд** — после входа админ попадает на обзорный экран с KPI по клиентам, проектам, остаткам и идентификациям. Дашборд подсвечивает клиентов в зонах `Предупреждение` / `Риск` / `Критично`, B4-блокировки, непривязанные лиды и ошибки проектных операций. Фильтры: период, клиент, источники A/B/C/D и включение клиентов агентов. На экране нет действий изменения данных, только переходы в существующие разделы.
11. **Manager: клиенты** — обзор по периоду, создание клиента, редактирование карточки, переход к проектам / очереди изменений / событиям ЧС / балансу; в таблице отдельно видны сбор данных, остаток/финансовый сигнал и ручной статус работы. У админа прямые клиенты разделены на **Активные клиенты** и сворачиваемый **Архив**: архив считается только по ручному статусу **Работа: Неактивен**, а остальные рабочие статусы остаются активными. Клик по строке у админа открывает popup **Сводка клиента** с показателями и быстрыми действиями, а кнопка **Карточка** остаётся редактором профиля клиента. У админа дополнительно есть пауза/возобновление **сбора** по клиенту, имперсонация и перевод клиента между админом и агентами; у агента — только свои клиенты.
12. **Админ: агенты** — создание/редактирование агента, включение/отключение, вход в ЛК агента, просмотр агрегированного остатка клиентов агента и списка закреплённых клиентов; в раскрытом списке клиентов агента используются те же статусы, что во вкладке «Клиенты».
13. **Manager: проекты** — фильтрация по клиенту, массовые действия, редактирование полей проекта (в т.ч. легаси-поля **статуса отгрузки** в данных), фильтр достижения дневного лимита проекта, переход к идентификациям клиента и к чёрному списку клиента; агент работает только с проектами своих клиентов.
14. **Manager: очередь изменений** — просмотр и **подтверждение (resolve)** записей в рамках доступных клиентов.
15. **Manager: баланс** — просмотр баланса клиента и тарифов; прямые ручные операции баланса клиента отключены, а изменение клиентского баланса выполняется через тарифные операции админа. В этом же сценарии админ создаёт тарифы, задаёт/редактирует `signal1/signal2/signal3`, смотрит список тарифов клиента и делает добавления/списания внутри конкретного тарифа. Агент может только смотреть тарифы и их историю у своих клиентов.
16. **Manager: история изменений** — админ видит события всех клиентов, агент — только своих. Лента объединяет успешные события, неуспешные проектные операции, баланс и отчёты; фильтры включают клиента, дату, тип события, статус и поиск.
17. **Админ: импорт лидов из XLSX** — выбор файла, **preview** (количество строк, валидные, уже существующие дубли в БД, готовые к импорту, проблемы с проектами); **импорт** только после успешного preview и только если нет строк без однозначного проекта и без неоднозначного совпадения проекта; перед записью данные снова валидируются на сервере, дедупликация по `vid`. Служебный **CLI**-скрипт в репозитории остаётся резервным вариантом (см. §7).
18. **Админ: проверка блокировок B4** — кнопка на админском экране проектов запускает проверку активных `B4` проектов у поставщика; та же проверка выполняется периодическим backend-фоном. Если `gck_project.result.status == 0` **или поставщик вернул пустой успешный ответ**, проект локально переводится в **Блокировка оператора**, пишется история и ставится Telegram outbox-уведомление. Сетевые ошибки и временные сбои поставщика проект автоматически не блокируют.

## 7. Интеграции и внешние системы

По **`README.md` репозитория** (не только по UI):

- **Prostats** — внешний API для операций с проектами (`PROSTATS_TOKEN` и др.); при создании проекта возможно несколько технических проектов на разные коды B1–B4; есть сценарий **уникальных имён** с внутренним идентификатором клиента. Для активных `B4` проектов backend дополнительно сверяет внешний статус через `gck_project`; `status == 0` и пустой успешный ответ трактуются как системная блокировка, сетевые ошибки — нет.
- **Telegram** — уведомления (тарифные сигналы остатка, автопауза по лимитам, техсобытия, B4-блокировки, достижение 100% дневного лимита проекта, успешные создание/изменение СМС-проектов) и доставка обращений из поддержки; backend пишет outbox, внешний `telegram_worker.py` отправляет сообщения; маршрут в чат клиента vs общий админский — см. §3.
- **Google Sheets** — экспорт (отдельный скрипт в репо, не экран ЛК).
- **Вебхук провайдера** — приём лидов на backend (`POST /api/provider-test/{secret}`), связь с проектом по имени страницы. Поиск проекта двухшаговый: сначала среди неудалённых, затем fallback к удалённым проектам с неистёкшим 48-часовым grace-окном. При отсутствии или неоднозначности совпадения лид сохраняется без `project_id`. Webhook старается **быстро принять и сохранить лид**, а лимит-контроль и тарифные сигналы выполняются отдельно по интервалу.
- **Вебхук Пикселя** — отдельный приём идентификаций с сайта клиента (`POST /api/pixel-webhook/{secret}`). Система ищет Пиксель-проект по домену из `site`; если домен найден однозначно, каждый телефон записывается как отдельная идентификация с URL страницы (`pixel_url`). Дедупликация для Пикселя — по паре `vid + phone`. Если домен не найден, найден неоднозначно или нет телефонов, идентификация не записывается и расход не считается.
- **Импорт лидов из XLSX (админский ЛК)** — восстановление или догрузка идентификаций из файла провайдера **без SSH**: двухшаговый API (preview → commit по временной сессии), общая бизнес-логика с вебхуком там, где это задумано (в т.ч. разбор `prov_chanel` / `prov_source` от имени проекта). Commit привязан к тому же админу, который создал preview, и запрещён при строках без однозначной привязки проекта. **Резерв:** скрипт `tool_import_provider_leads_from_xlsx.py` для ручного запуска с сервера.

Экран **Интеграции** — маркетинговый текст и сценарий «написать в поддержку». **Автоматической интеграции с CRM в ЛК нет**; всё, что выходит за рамки ручной настройки командой, **не заявлено** (ответ разработчика: нет).

## 8. Ограничения и неочевидное

- **Маршрутизация SPA:** почти все разделы без отдельного URL — при обновлении страницы откроется последнее сохранённое в `localStorage` представление (кроме логина).
- **Админский дашборд** — только для администратора (`user.id == 1`). Его агрегаты считаются на backend через `GET /admin/dashboard`; не нужно собирать управленческую сводку на frontend из больших таблиц. Основные KPI по полученным данным считают только привязанные `provider_leads`, а непривязанные лиды показываются отдельным риском.
- **Клиентский дашборд** — первый экран клиента после логина. Его агрегаты считаются на backend через `GET /dashboard`; frontend не должен пересчитывать эту сводку из больших списков идентификаций.
- **Дубликаты доменов/номеров** между проектами — бэкенд возвращает структурированную ошибку; фронт показывает список конфликтов.
- **Пиксель** — это не отдельный продукт и не отдельный раздел. Он живёт в обычных проектах/идентификациях клиента как источник сбора **Пиксель**. Канал A/B/C/D к нему не применяется; в таблице идентификаций канал показывается как `—`.
- **Пиксель-проект** — домен должен совпадать с `site`, приходящим в webhook. Если домен нужно поменять, создаётся новый проект; старый не переименовывается.
- **Авто-контроль лимитов** — при несоответствии суммы лимитов активных проектов и остатка бэкенд **отключает проекты с наибольшего лимита**; при включении проекта клиентом фронт может показать отказ с текстом про сумму лимитов и остаток.
- **Дневной лимит проекта** и **остаток тарифа клиента** — разные контуры. Дневной лимит смотрит на количество идентификаций проекта за день/период и используется для фильтра `dailyLimitReached` и Telegram-сигнала 100%; остаток клиента (`remaining`) используется для тарифных сигналов и автопаузы.
- **Тарифы и баланс** — это два связанных контура: тарифные операции зеркалятся в баланс клиента, поэтому меняют `remaining`, участвуют в лимит-контроле и могут влиять на автопаузу. Telegram-сигналы `signal1` и `signal2` обязательны, `signal3` необязателен; сигналы проверяются периодическим фоном для всех клиентов, а не мгновенно на каждый новый лид.
- **Финансовые статусы клиентов** — `Дожим 1/2/3` и `Долг` показываются только при наличии тарифа. Если тарифа нет, в таблице остаётся число остатка без финансового бейджа.
- **Рабочий статус клиента** — ручной статус менеджера, не автоматический. Его могут менять админ и агент для доступных клиентов; автоматика по балансу, тарифам или проектам его не перезаписывает.
- **Архив клиентов в админке** — UI-группировка прямых клиентов админа, а не отдельный backend-статус. Клиент попадает в архив только при ручном статусе **Работа: Неактивен**; смена баланса, тарифов, проектов или статуса сбора данных не архивирует клиента автоматически.
- **Агентский уровень** — это не отдельный продукт, а manager-режим поверх тех же `/admin/*`; ограничения агента обязательно проверяются на backend, а не только скрываются в UI.
- **Агентский баланс** — не самостоятельный баланс и не долг агента; это агрегированная сумма текущих остатков клиентов агента.
- **Отключение агента** — это два разных эффекта: запрет входа самому агенту и блокировка редактирования проектов у его клиентов. При повторном включении агента блокировка редактирования снимается, но сами проекты автоматически не активируются.
- **Системная блокировка B4** — `Блокировка оператора` выставляется backend-проверкой только для активных `B4` проектов, если поставщик вернул `result.status == 0` или пустой успешный ответ. Сетевые ошибки проект автоматически не блокируют. Этот статус нельзя выбирать вручную и нельзя применять к B1/B2/B3 без отдельного решения.
- **Display-коды источников** — пользователю frontend показывает A/B/C/D, но API, БД, webhook, XLSX, Prostats и экспортная логика используют raw-коды B1/B2/B3/B4. Пиксель фильтруется отдельно по источнику сбора, а не как технический канал `P`.
- **Внутренний идентификатор клиента в имени проекта** — применяется только к новым проектам клиентов с `unique_project_names_enabled=true`; старые `[MB{id}]`-проекты остаются legacy и не переименовываются.
- **`lk id` идентификаций** — публичный вычисляемый ID для ЛК/отчётов/Google Sheets, не отдельная колонка БД; для сверки с провайдером остаётся `vid` / `ext_id`.
- **XLSX preview/commit** — preview-артефакты лежат локально у процесса backend; при нескольких инстансах без sticky session preview на одном узле и commit на другом не сработают.
- Разделы **Обучение** и **Онбординг** — только заглушки в UI; **наполнение и сроки отложены** (ответ разработчика).
- Кнопка **WhatsApp** на экране техподдержки ведёт на **тот же URL, что и Telegram** — **намеренная заглушка**, отдельной ссылки на WhatsApp пока нет.
- **Импорт лидов (админ):** запись в БД возможна только после **preview** и отдельного подтверждения; если в сводке есть необработанные проекты (`notFoundProjects`) или неоднозначные совпадения (`ambiguousProjects`), кнопка импорта недоступна до исправления файла.

| Дашборд | клиентский обзорный экран `GET /dashboard` / `ClientDashboard` или админский обзорный экран `GET /admin/dashboard` / `AdminDashboard` |
| Сбор данных | статус по проектам клиента: Нет проектов / Сбор активен / На паузе |
| Работа | ручной рабочий статус клиента: В работе / Ждём оплату / Ждём данные / На согласовании / Пауза по клиенту / Неактивен |
| Финансовый бейдж клиента | Дожим 1 / Дожим 2 / Дожим 3 / Долг; показывается в колонке Остаток только при наличии тарифа |
| Начисление / списание (баланс) | `credit` / `debit` |
| Тариф | `ClientTariff`, клиентский тарифный контур, который зеркалит изменения в баланс клиента и содержит `signal1/signal2/signal3` |
| Очередь изменений | `admin/changes`, статусы pending/done |
| Импорт лидов (админ) | XLSX, эндпоинты `admin/provider-leads-import` (preview / commit), временная сессия по `previewId` |
| Блокировка оператора | системный output-статус активного B4-проекта после проверки поставщика (`status == 0` или пустой успешный ответ) |

## Что агенту ТЗ не стоит выдумывать

По ответам разработчика закрыто в том числе: **CRM** (автоинтеграции нет), **WhatsApp** (заглушка = тот же URL, что Telegram), **Обучение / Онбординг** (отложено, без утверждённого содержания).

Остаётся не выдумывать от себя:

- **Детальные пороги и полный перечень типов** уведомлений (колокол, Telegram и т.д.) — при жёстком ТЗ сверять с **бэкендом** и кодом.
