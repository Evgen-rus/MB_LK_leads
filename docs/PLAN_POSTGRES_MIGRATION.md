# План перехода на PostgreSQL

Ниже пошаговый план перехода с SQLite на PostgreSQL, чтобы всё работало
так же, как сейчас, без поломок.

## Важное влияние
- Меняется тип БД и строка подключения.
- Любая существующая локальная `app.db` больше не используется.
- Миграции не применяются: схема создаётся через `create_all`, а минимальные данные — через seed.

## Шаги

1. **Подготовить PostgreSQL**
   - Установить PostgreSQL локально.
   - Создать базу данных и пользователя.
   - Зафиксировать параметры доступа: host, port, dbname, user, password.

2. **Настроить `DATABASE_URL`**
   - В `.env` добавить строку подключения:
     `postgresql+psycopg2://USER:PASSWORD@HOST:PORT/DBNAME`
   - Убедиться, что приложение читает `DATABASE_URL` (сейчас оно это делает).

3. **Добавить драйвер PostgreSQL**
   - В `requirements.txt` добавить `psycopg2-binary` (или `psycopg`).
   - Установить зависимости.

4. **Адаптировать создание таблиц**
   - Оставить `models.Base.metadata.create_all()` для начальной схемы.
   - Миграции `ensure_*` не используются, остаётся только seed.

5. **Проверить совместимость запросов**
   - Прогнать ключевые CRUD-операции.
   - Проверить, нет ли SQLite-специфичных SQL-запросов.

6. **Инициализировать минимальные данные (seed)**
   - Создать служебную запись `notify_state`.
   - Создать пользователей из `.env`, если они нужны для входа.

7. **Тестирование**
   - Запустить backend и пройти основные сценарии:
     логин, проекты, лиды, отчёты, админский раздел.

8. **Очистка и фиксация**
   - Убедиться, что `app.db` больше не используется.
   - Зафиксировать параметры подключения для dev-окружения.

## Риски и как снизить
- **Средний риск**: возможны ошибки в SQL, отличающиеся от SQLite.
- Снизить риск можно тестами основных сценариев.

## Итог
После перехода приложение работает на PostgreSQL с тем же API и логикой,
а схема создаётся через `create_all`, а минимальные данные — через seed.
