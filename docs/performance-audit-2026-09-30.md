## Метод и ограничения

- VPS LeadRecord, приложение `/opt/MB_LK_leads`, commit `c6f00e3`. Проверенные backend и frontend исходники совпадают с локальными после нормализации CRLF/LF.
- Один Uvicorn, PostgreSQL 16. Load average 0,32; доступная RAM около 1,3 ГБ. Статистика PostgreSQL: примерно 134297 лидов, 4352 проекта, 32834 события аудита, 40 пользователей, 104 отчёта. Это оценки `n_live_tup`, а не точные COUNT.
- Каждый основной GET API выполнялся последовательно три раза через loopback, без конкурентной нагрузки. Указаны медиана и диапазон, не p95. Время включает чтение тела ответа; не включает интернет до устройства, загрузку JS, React и отрисовку.
- SQL измерялся отдельно на production-данных через production CRUD, без импорта `main.py` и запуска startup/schema-evolution. Диагностические соединения: `default_transaction_read_only=on`, `statement_timeout=5000`, `lock_timeout=1000`. Сессии завершались rollback.
- SQL-время ниже — сумма времени DBAPI cursor execute: включает драйвер/передачу, исключает последующую ORM-материализацию. Это отдельные прогоны, поэтому вычитать его из API-времени как точную декомпозицию нельзя.
- Три ограниченных `EXPLAIN ANALYZE` применены только к SELECT. Секреты для штатной авторизации использовались внутри процесса и не сохранялись в отчёт. Тела API, персональные данные и значения SQL-параметров не сохранялись.
- Сводная измерена для клиента с наибольшим числом привязанных лидов. Это один крупный клиент, не выборка всех клиентов.

## Где теряется время

### 1. Сводная: полная история ради пяти событий

`client_dashboard` вызывает `list_client_activity_events(limit=5)`, но `list_activity_events_for_clients` сначала загружает все подходящие события четырёх источников, строит описания и Pydantic-объекты, сортирует в Python и лишь затем делает slice.

В отдельном замере: сводная 1079,62 мс; история 896,67 мс (83%); материализовано 2291 событие, возвращено 5. Audit SELECT вернул 2203 широкие строки с before/after и Project; cursor execute 230,30 мс. PostgreSQL EXPLAIN: 48,88 мс, Seq Scan audit_events и Hash Join, плановая ширина результата 2023 байта. Загрузка/декодирование/ORM и Python-обработка объясняют существенную часть задержки сверх собственно SQL.

Предложение: ограничить получение последних событий на стороне SQL до построения описаний. Для сводной без поиска можно взять последние пять из каждого источника, объединить и выбрать общие пять; применять существующие фильтры до LIMIT. Сохранить права, очистку внутренних названий и порядок при одинаковых датах. Общая история также использует этот код: её поиск, total и offset нельзя сломать простым LIMIT всей функции.

Выигрыш пока не измерен. Верхняя граница устраняемой работы в данном прогоне — 897 мс; это не обещание такого ускорения. После реализации проверить эквивалентность пяти событий и bounded SQL row count на большой синтетической истории.

### 2. Клиенты: повторные профили и повторные агрегаты

`admin_clients_summary` вызывает `_get_user_info(db, 1)` в цикле для admin-owned клиентов. Подтверждены 38 повторных profile SELECT. Предложение: загрузить owner admin один раз до цикла. Для измеренного auth-подобного контекста ожидаемое число CRUD SQL: 54 → 17, если заменить 38 вызовов одним. Выигрыш в миллисекундах не измерен; N+1 не является единственным и главным расходом здесь.

Pending summary делает четыре прохода по audit_events. UI дополнительно вызывает тот же summary отдельным GET, пока основной summary уже считает его. EXPLAIN одного pending SELECT: 29,93 мс, Seq Scan 32834 строк для 105 результатов; 7371 shared hit blocks. Отдельный changes GET занимает около 146 мс и запускается параллельно, поэтому его удаление не означает автоматического ускорения экрана на 146 мс.

Предложения по одному за раз: условная агрегация pending в одном SQL; затем проверка возможности переиспользовать полный pending payload вместо второго GET. Частичный индекс для необработанных audit events — кандидат, но эффект не проверен и изменение БД требует отдельного разрешения. Индекс первым шагом не предлагается.

All-time aggregate лидов — ещё около 102 мс cursor в одном прогоне; EXPLAIN 127,51 мс. Уже используется index-only scan по `ix_provider_leads_project_id`. Отсутствующий индекс здесь не подтверждён; кэш/денормализация пока не оправданы.

API списка клиентов не имеет серверной пагинации и отправляет 30-дневные серии всех четырёх источников для всех 38 клиентов. UI пагинирует локально. При этом сводная выбранного клиента переиспользует загруженные данные. Есть лишняя доставка графиков для невыбранных клиентов, но разделение payload потребует изменения контракта и нового запроса; без browser/network baseline это не первый шаг.

Через nginx ответ application/json не сжимается даже с `Accept-Encoding: gzip`: 204965 байт, Content-Encoding отсутствует. Добавление JSON в gzip_types — кандидат для сетевого улучшения, но конфигурация не менялась, эффект на пользовательской сети не измерен.

### 3. Идентификации

SQL-пагинация существует; индекс imported_at существует; проекты и пользователи подгружаются пакетно, N+1 в просмотренном потоке не найден. API быстрый, добавлять индексы/кэш для этих измеренных запросов не обосновано.

По frontend-коду обычное открытие инициирует users + leads. Эффект для пустого userId вызывает `setProjectIds([])` новым массивом, что снова меняет зависимость load и может дать повторный GET leads. Prefill и загрузка проектов могут добавлять запросы. При выборе клиента UI запрашивает до 10000 проектов, реальный потолок и размер этого ответа отдельно не замерялись. Сначала подтвердить дубли в browser network waterfall, затем убрать лишний сброс состояния.

### 4. Отчёты

Список пагинирован, связанная информация пользователей загружается пакетно. При текущих 104 отчётах API быстр. Открытие UI: users + reports; смена pageSize вновь вызывает users. Это небольшой лишний запрос, а не подтверждённый bottleneck.

## Приоритет и риски

1. Первое содержательное улучшение: bounded recent-events для сводной. Здесь самый большой доказанный расход. Основной риск — семантика общей истории, фильтров и равных timestamps; обязательны сравнение результата и guardrail по объёму выборки.
2. Затем отдельным небольшим изменением устранить N+1 owner profile. Риск: сохранить все поля ownerUser и null fallback. Guardrail — число SQL не растёт с количеством admin-owned клиентов.
3. Затем объединить pending aggregate и проверить дубли API. Риск: сохранить раздельные счётчики create/update/delete/blacklist и агентские права.
4. JSON gzip — отдельная конфигурационная задача после разрешения на production-изменения и проверки сети. Индексы — только после отдельного обоснования и разрешения.
