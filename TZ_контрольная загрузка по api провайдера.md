
## 1. Как сейчас реализовано

- **Приём лидов:** провайдер шлёт вебхук на `POST /api/provider-test/{secret}` с JSON: `vid`, `phone`, `page` (имя проекта), `time` (Unix-строка), и т.д.
- **Дедуп при записи:** если лид с таким **`vid` уже есть** в таблице `provider_leads` — новая строка **не создаётся**, ответ `duplicate`. В БД на `vid` стоит **уникальный** индекс.
- **Время лида в БД:** из поля `time` делается `prov_created_at` функцией `_parse_provider_time`: Unix → момент в UTC → **плюс 3 часа** (в коде это задумано как сдвиг к «МСК по часам»). Пустой/битый `time` → `prov_created_at` может быть `NULL`.
- **Импорт из XLSX (админ/CLI):** отдельный поток, дубли тоже в основном по **`vid`**.
- **Сторона провайдера для сверки:** у тебя уже есть скрипт `util_14_gck_phones_dump.py`, который дергает их API и получает за **день по `project_id`** список вида `phone` + `created_at` (как в твоём JSON).

## 2. Для чего и что нужно сделать

**Зачем:** не заменять дедуп по `vid`, а сделать **дополнительную проверку полноты** — «все ли лиды за выбранный день по проекту, которые видит провайдер в API, дошли к нам в `provider_leads`» (и наоборот: у нас есть, у провайдера нет — тоже полезно понимать).

**Что сделать (суть):** для выбранных **даты** и **проекта** (по `provider_project_id` / id у провайдера):

1. Получить множество «ключей» с **стороны API** (телефон + календарная дата без времени; проект задан контекстом запроса).
2. Построить множество «ключей» **из нашей БД** за тот же день и тот же проект: **`phone` + `project_name` (или сопоставление с тем же проектом) + календарная дата** из `prov_created_at` (и правило на случай `NULL` — например `imported_at` или отдельная метка «без даты провайдера»).
3. Сравнить: **только в API**, **только у нас**, **пересечение**.

Ключ сравнения ты уже определил: **не полное время**, а **день** — потому что между вебхуком и API видна расхождение по минутам при том же лиде.

## 3. Что учесть при реализации

| Тема | Смысл |
|------|--------|
| **Проект** | В дампе API проект — это **id запроса**. В БД — `project_id` и/или строка `project_name` из `page`. Нужно однозначно сопоставить «этот `project_id` API = этот наш проект» (через `Project.provider_project_id`). |
| **Имя проекта в ключе** | Для строк из API имя не в каждой записи — оно из контекста. Для строк из БД — то, что сохранено (`page` как `project_name`). Имена должны быть **согласованы** с тем, как ты фильтруешь «лиды этого проекта». |
| **Дата** | Календарный день для **наших** записей брать **так же**, как при записи вебхука (из `prov_created_at` после той же логики парсинга `time`). Для **API** — понять, в какой зоне трактовать `created_at` (если без `Z`/offset — зафиксировать правило, например «как у провайдера / МСК»). |
| **Полночь** | Если зоны разъедутся, **день** редко может различиться у границы суток — для большинства лидов не критично, но для отчёта «строго за сутки» стоит явно описать правило. |
| **`prov_created_at` = NULL** | Решить: не попадает в сверку, отдельный список «без даты», или fallback на `imported_at`. |
| **Телефон** | Если везде один формат (`7926...`) — можно сравнивать строкой; если появятся варианты — одна функция нормализации. |
| **Не путать с дедупом** | Это **офлайн/периодическая сверка** (или админская кнопка/CLI), а не замена проверки по `vid` в вебхуке. |
| **Объём** | Для больших дней — пакетная выборка из БД, без загрузки всех лидов в память сразу, если проектов много. |
