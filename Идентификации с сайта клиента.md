# ТЗ: Добавить источник сбора «Пиксель» в текущие проекты и идентификации

## Цель

Добавить в текущий ЛК новый источник сбора **«Пиксель»**.

**Пиксель** — это новый тип проекта, который собирает идентификации пользователей, заходивших на сайт клиента.

Важно: не делать отдельный продукт, отдельный ЛК, отдельные разделы «Пиксель клиенты / Пиксель проекты / Пиксель идентификации». Нужно максимально переиспользовать то, что уже работает:

* текущий раздел **Клиенты**;
* текущий раздел **Проекты**;
* текущий раздел **Идентификации**;
* текущий баланс и тарифы;
* текущие права доступа админа, агента и клиента;
* текущую историю изменений;
* текущую механику локального создания/редактирования проектов по аналогии с СМС.

Главная идея: **Пиксель — это новый источник сбора в обычном проекте клиента**.

* Python-файл компилируется;

# Проекты Пикселя

## Что такое проект Пикселя

**Один проект Пикселя = один домен сайта клиента.**

Примеры:

* `realestatesale.ae`
* `creek-harbour-dubai.ru`
* `estate-tai.ru`

Админ создаёт обычный проект клиента, но выбирает:

**Источник сбора: Пиксель**

---

## Название проекта

Название проекта админ задаёт сам.

При этом для проекта Пикселя:

* домен берётся из названия проекта;
* домен после создания менять нельзя;
* название проекта менять можно;
* если нужно изменить домен, нужно создать новый проект Пикселя.

Это нужно, чтобы входящие идентификации стабильно привязывались к проекту по домену.

---

## Форма создания проекта Пикселя

В текущей форме создания проекта добавить значение:

**Источник сбора: Пиксель**

Если выбран **Пиксель**, форма должна быть максимально похожа на источник сбора **Сайты**, но с упрощением.

### Оставить для Пикселя

* название проекта;
* источник сбора: **Пиксель**;
* статус проекта;
* лимит;
* дни получения номеров;
* остальные общие поля проекта, которые уже используются и подходят для текущей логики.

### Скрыть / не использовать для Пикселя

* **Источник данных A / B / C / D**;
* список сайтов конкурентов;
* список телефонов конкурентов;
* поля, которые нужны только для конкурентного сбора.

---

## Статусы проекта Пикселя

Для проекта Пикселя используются текущие статусы проекта:

* **Активен**;
* **На паузе**;
* **Удалён**.

Статус проекта не должен блокировать запись входящих идентификаций, если домен найден однозначно.

Причина: данные могут приходить позже, в том числе после постановки проекта на паузу или удаления.

---

## Создание и редактирование проекта Пикселя

Для проектов Пикселя используем логику по аналогии с СМС-проектами:

* проект создаётся в нашей БД;
* изменения сохраняются в нашей БД;
* изменения пишутся в историю;
* создание/редактирование не отправляется во внешний API поставщика;
* админ вручную настраивает проект у поставщика в их личном кабинете.

Отдельный бейдж **«Требует ручной настройки»** не нужен.

Достаточно записи в истории, как для СМС.

# Webhook Пикселя

## Общая логика

Для Пикселя нужен отдельный webhook/API, потому что данные приходят от другого источника и в другом формате.

При этом результат обработки должен попадать в общий контур идентификаций.

---

## Пример входящего payload

```json id="s6qkkj"
{
  "ip": "84.53.216.180",
  "utm": {
    "etext": "2202.6qf3FRKavXpE2R7gQj2r-",
    "yclid": "13460990782546116607",
    "utm_term": "---autotargeting",
    "utm_medium": "cpc",
    "utm_source": "yandex",
    "utm_content": "d_d4|17742677997|5758980034|205758980034|none|search",
    "utm_campaign": "710576260"
  },
  "vid": "1689220848",
  "page": "https://realestatesale.ae/dubai-podbor?yclid=13460990782546116607&utm_campaign=710576260",
  "site": "realestatesale.ae",
  "time": "1781071998",
  "device": "Mobile Phone",
  "phones": ["79209160716"],
  "browser": "Chrome",
  "comment": null,
  "platform": "Android"
}
```

---

## Ожидаемые поля

* `vid` — внешний идентификатор события/визита;
* `site` — домен сайта клиента;
* `page` — полный URL страницы;
* `phones` — массив телефонов;
* `time` — время события у источника;
* `utm` — рекламные метки;
* `ip` — IP пользователя;
* `device` — устройство;
* `browser` — браузер;
* `platform` — платформа;
* `comment` — комментарий, если приходит.

---

## Дедупликация

Уникальность идентификации Пикселя определяется по связке:

**`vid + телефон`**

Правила:

1. Если `vid` одинаковый и телефон одинаковый — это дубль.
2. Если `vid` одинаковый, но телефон другой — это новая идентификация.
3. Если в одном payload пришло несколько телефонов, каждый телефон обрабатывается отдельно.
4. За дубли повторное списание не выполняется.

---

## Payload с несколькими телефонами

Если пришло:

```json id="je6tm6"
{
  "vid": "1689861701",
  "site": "realestatesale.ae",
  "phones": ["79031234567", "79039876543"]
}
```

Система должна обработать это как две идентификации:

1. `1689861701 + 79031234567`
2. `1689861701 + 79039876543`

Если обе связки новые:

* создаются 2 идентификации;
* из остатка клиента списывается 2 единицы.

# Привязка идентификаций Пикселя к проекту

## Основное правило

Идентификация Пикселя привязывается к проекту по домену из поля:

**`site`**

Система должна искать проект с источником сбора **Пиксель**, у которого домен соответствует `site`.

---

## Порядок поиска проекта

1. Сначала искать среди неудалённых проектов Пикселя.
2. Если среди неудалённых проектов совпадение не найдено — искать среди удалённых проектов Пикселя.
3. Если найден один подходящий проект — идентификация записывается.
4. Если домен не найден — идентификация не записывается в ЛК.
5. Если домен найден неоднозначно — идентификация не записывается в ЛК.

---

## Поведение по статусам

Если домен найден однозначно, идентификацию записываем независимо от статуса проекта:

* **Активен** — записываем;
* **На паузе** — записываем;
* **Удалён** — записываем, если проект определён однозначно.

---

## Если домен не найден

Если в `site` пришёл домен, которого нет среди проектов Пикселя:

* идентификация не попадает в ЛК;
* остаток клиента не списывается;
* событие фиксируется в служебной диагностике.

Автоматически создавать проект по неизвестному домену не нужно.

---

## Если домен найден неоднозначно

Если один домен подходит к нескольким проектам и система не может выбрать один проект:

* идентификация не попадает в ЛК;
* остаток клиента не списывается;
* событие фиксируется в служебной диагностике.

# Баланс

## Общая логика

Идентификации Пикселя списываются из общего остатка клиента.

Отдельный тариф или отдельный баланс для Пикселя не нужен.

---

## Правила списания

1. Одна новая идентификация Пикселя = списать 1 единицу из остатка клиента.
2. Если в payload один новый телефон — списать 1.
3. Если в payload три новых телефона — создать 3 идентификации и списать 3.
4. Если телефон является дублем по связке **`vid + телефон`** — не списывать.
5. Если домен не найден — не списывать.
6. Если домен найден неоднозначно — не списывать.
7. Если проект найден в статусе **Активен** — списывать.
8. Если проект найден в статусе **На паузе** — списывать.
9. Если проект найден в статусе **Удалён** — списывать, если проект определён однозначно.

---

# История изменений

Для проектов Пикселя использовать текущую историю изменений.

Записывать события:

* создан проект Пикселя;
* изменён проект Пикселя;
* проект Пикселя поставлен на паузу;
* проект Пикселя активирован;
* проект Пикселя удалён.

Отдельный бейдж **«Требует ручной настройки»** не нужен.

Создание и редактирование проекта Пикселя должны попадать в историю по аналогии с СМС-проектами.

---

# Служебная диагностика webhook Пикселя

Нужен служебный журнал обработки входящих данных Пикселя.

В журнале фиксировать:

* дату и время получения;
* домен из `site`;
* `vid`;
* количество телефонов в payload;
* результат обработки;
* причину, если данные не попали в ЛК.

Возможные результаты:

* записано;
* дубль;
* домен не найден;
* домен неоднозначен;
* нет телефонов;
* некорректный формат;
* ошибка обработки.

Для первой версии достаточно служебной диагностики. Отдельный полноценный экран ошибок можно не делать, если это увеличивает объём задачи.

* переделку текущего webhook конкурентных идентификаций;
* изменение дашборда;
* изменение отчётов;
* отдельные графики Пикселя;
* аналитику по UTM;
* автоматическое создание проекта по неизвестному домену;
* отправку создания/редактирования Пиксель-проекта во внешний API поставщика.

Главное ограничение: **не переделывать то, что уже работает, а встроить Пиксель в существующую механику.**

# Критерии приёмки

## Проекты

1. В форме проекта появился источник сбора **Пиксель**.
2. Админ может создать проект с источником сбора **Пиксель**.
3. Один проект Пикселя соответствует одному домену.
4. Домен берётся из названия проекта.
5. После создания домен проекта Пикселя нельзя изменить.
6. Название проекта можно изменить.
7. Для Пикселя не показывается источник данных A/B/C/D.
8. Для Пикселя не показывается список сайтов/номеров конкурентов.
9. Лимит, статус и дни получения работают по текущей логике проекта.
10. Проект Пикселя сохраняется локально в нашей БД.
11. Создание/редактирование проекта Пикселя не отправляется во внешний API поставщика.
12. Создание/редактирование проекта Пикселя пишется в историю.

## Webhook

13. Создан отдельный webhook/API для Пикселя.
14. Webhook принимает JSON с `vid`, `site`, `page`, `phones`, `time`, `utm`.
15. Один payload с несколькими телефонами обрабатывается как несколько потенциальных идентификаций.
16. Дедупликация работает по связке **`vid + телефон`**.
17. Повторная связка **`vid + телефон`** не создаёт новую идентификацию и не списывает остаток.

## Привязка к проекту

18. Система ищет проект Пикселя по домену из `site`.
19. Сначала проверяются неудалённые проекты.
20. Если среди неудалённых нет совпадения, проверяются удалённые проекты.
21. Если проект найден однозначно, идентификация записывается.
22. Если домен не найден, идентификация не записывается.
23. Если домен найден неоднозначно, идентификация не записывается.
24. Статус проекта **Активен / На паузе / Удалён** не блокирует запись, если проект найден однозначно.

## Идентификации

25. Идентификации Пикселя отображаются в общем разделе **Идентификации**.
26. В таблице идентификаций есть колонка **Источник сбора**.
27. Для строк Пикселя в колонке **Источник сбора** указано **Пиксель**.
28. В разделе **Идентификации** есть фильтр по источнику сбора.
29. Через фильтр можно вывести только **Пиксель**.
30. В основной таблице не выводятся все UTM-поля отдельными колонками.
31. Для строки Пикселя доступна карточка **Подробнее**.
32. В карточке **Подробнее** показываются URL, UTM, yclid, устройство, браузер, платформа, IP и статус интеграции.

## Баланс

33. Каждая новая идентификация Пикселя списывает 1 единицу из общего остатка клиента.
34. Если в payload пришло 3 новых телефона, создаётся 3 идентификации и списывается 3 единицы.
35. За дубли списание не выполняется.
36. За данные с неизвестным доменом списание не выполняется.
37. За данные с неоднозначным доменом списание не выполняется.

## Права доступа

38. Админ видит все проекты и идентификации Пикселя.
39. Агент видит только проекты и идентификации Пикселя своих клиентов.
40. Клиент видит только свои проекты и идентификации Пикселя.
41. Отдельные права доступа для Пикселя не вводятся, используется текущая модель прав.

# Открытые вопросы

Критичных открытых вопросов для запуска нет.

После тестового webhook можно дополнительно уточнить:

1. Нужно ли хранить raw payload успешных событий постоянно или только временно.
2. Нужен ли отдельный экран служебных ошибок webhook Пикселя или достаточно логов/диагностики.
