# План: интеграция API поставщика Prostats (создание/редактирование проектов)

## Контекст (как я понял)

- **Наш ЛК**: клиент создаёт/редактирует “проекты” и потом получает лиды.
- **Поставщик (Prostats)**: теперь даёт API, через которое можно **создавать и редактировать проекты у поставщика**.
- Цель: **объединить** наш “создать/обновить проект” так, чтобы при работе клиента в нашем ЛК мы **параллельно** создавали/обновляли проект у поставщика через его API.

Важно: токен/URL поставщика должны жить **только на бэкенде** (в env). Фронт их видеть не должен.

## Что умеет API поставщика (по документации/примерам)

Один endpoint: `PROSTATS_API_URL` (по умолчанию `https://prostats.info/api/index.php`).

Запрос `POST JSON` вида:

- **Создание**: `{ token, command: "gck_project_create", ...поля... }`
- **Обновление**: `{ token, command: "gck_project_update", id, ...поля... }` (поля можно слать частично)

### Поля create (обязательные)

- `type`: `"hosts"` (сайты) или `"calls"` (звонки); для “Пересечение” есть `type="complex"`
- `src`: `"mt" | "bl" | "rt" | "mg"` (источник данных)
- `name`: название проекта
- `limit`: дневной лимит (число)
- `content`: список сайтов/номеров (строка через запятую; в примерах допускается массив, но скрипт всё равно превращает в строку)
- `status`: `1` активен, `0` не активен
- `tag`: по доке “важно ставим точная копия name”
- `is_crm`: по доке “всегда 0 (посетитель)”

### Поля create/update (опциональные)

- `workdays`: `"1234567"` или массив `[1..7]`
- `regions`: массив чисел (например `[50, 77]`)
- `regions_reverse`: `0` включить регионы из списка, `1` исключить регионы из списка

### Маппинг “src → префикс”

Из доки:
- `mt` → у них в ЛК проект создастся с префиксом **B3_**
- `bl` → **B2_**
- `rt` → **B1_**
- `mg` → **B4_**

Про **B4** подтверждено: `src="mg"`.

## Ключевая идея интеграции

Все действия клиента остаются “через наш бэкенд”.

- Клиент нажал **Создать** в нашем ЛК → наш бэкенд создаёт проект(ы) в нашей БД → затем вызывает `gck_project_create` у поставщика → **берёт `id` из ответа** → сохраняет у себя соответствие “наш project.id → id у поставщика”.
- Клиент нажал **Сохранить** в нашем ЛК → наш бэкенд обновляет проект в нашей БД → затем вызывает `gck_project_update` у поставщика (по сохранённому id) → фиксирует результат.

## План работ (по шагам)

### Шаг 1. Определить точный маппинг наших полей на поля Prostats

Нужно решить и зафиксировать правила:

- `collectionSource` (у нас) → `type` (у них):
  - `"Сайты"` / `"Ретросайты"` → `type="hosts"`
  - `"Звонки"` / `"Ретрозвонки"` → `type="calls"`
  - `"Пересечение"`: подтверждено как отдельный режим у поставщика:
    - `type="complex"`
    - ограничение: **только B2** (`src="bl"`)
    - `content` — JSON-строка с полями `hosts_content`, `calls_content`, `sms_content` и др.

- `dataSourceCode` (у нас `B1/B2/B3/B4`) → `src` (у них `rt/bl/mt/mg`):
  - `B1 → rt`, `B2 → bl`, `B3 → mt`, `B4 → mg`

- `sites/phones` → `content`:
  - превращаем в строку `",".join(...)`
  - для сайтов желательно нормализовать (убрать `https://`, `http://`, путь) — чтобы отправлять “чистые домены”

- `status`:
  - `"Активен" → 1`, `"На паузе" → 0`

- `days` (у нас `'Пн'..'Вс'`) → `workdays`:
  - маппинг: `Пн=1, Вт=2, Ср=3, Чт=4, Пт=5, Сб=6, Вс=7`
  - собираем строку например `"12345"`

- `regions` (у нас сейчас имена регионов) → `regions` (у них коды):
  - потребуется таблица соответствия “имя → код” (как в доке)
  - если у нас регион “Москва и область” vs “г. Москва” — надо унифицировать значения
  - если маппинга нет — либо блокировать сохранение, либо пропускать регионы (сбор по всей РФ)

Риск: **высокий** для регионов и режима “Пересечение” (нужно строгое соответствие формату `content`).

### Шаг 2. Добавить хранение связи с проектом поставщика в нашу БД

Минимально нужно хранить:

- `provider_name` (например `"prostats"`)
- `provider_project_id` (id, который нужен для `gck_project_update`)
- `provider_src` и `provider_type` (чтобы понимать, что именно мы создавали)
- `provider_last_sync_at`, `provider_last_sync_status`, `provider_last_sync_error` (для диагностики)

Так мы не потеряем “id у поставщика” и сможем делать update. Важно: `gck_project_create` **возвращает `id`** (см. лог `gck_api_log_2026-01-26_183343.txt`), поэтому поиск по списку проектов не нужен для стандартного кейса.

### Шаг 3. Реализовать HTTP-клиент Prostats на бэкенде

Сделать небольшой модуль, например:

- `backend/app/providers/prostats.py`
  - `create_project(payload) -> response`
  - `update_project(id, payload_patch) -> response`

Требования:

- токен берём из env `PROSTATS_TOKEN`
- URL из env `PROSTATS_API_URL`
- таймауты, логирование, понятные ошибки
- никаких токенов в логах

### Шаг 4. Встроить вызовы Prostats в наши CRUD-операции проектов

Вариант реализации (самый простой):

- **Создание проекта**:
  - создаём проект в нашей БД
  - вызываем `gck_project_create`
  - берём `provider_project_id` из ответа и сохраняем
  - если `id` не пришёл — помечаем sync-статус и показываем пользователю “проект создан у нас, но не создан у поставщика”

- **Редактирование проекта**:
  - обновляем нашу БД
  - вызываем `gck_project_update` только по изменившимся полям (можно вычислить diff)
  - фиксируем результат

Более надёжный вариант (на будущее):

- класть “событие синхронизации” в таблицу/очередь и обрабатывать воркером (ретраи, dead-letter).

Риск: **средний** (если API поставщика временно недоступен, нужно правильно разрулить частичный успех).

### Шаг 5. UI/поведение для пользователя

Чтобы клиенту было понятно, что происходит:

- при создании/обновлении показывать статус:
  - “Сохранено”
  - “Сохранено, но синхронизация с поставщиком не прошла” (с текстом ошибки)
- (опционально) кнопка “Повторить синхронизацию”

### Шаг 6. Тестирование на стенде

- отдельные ручные проверки:
  - создать проект “Сайты” для `B1/B2/B3` → проверить, что у поставщика реально появился проект
  - обновить `limit/status/workdays/regions` → проверить, что изменения применились
- негативные кейсы:
  - неправильные регионы
  - пустой content
  - отключенный token/URL

## Вопросы, которые нужно уточнить у поставщика (короткий список)

1) **B4**: подтверждено, `src="mg"` (соответствует B4).
2) **Пересечение**: подтверждено как `type="complex"`, **только B2** (`src="bl"`). `content` — JSON-строка:

```
{"hosts_content":"test202312261.ru","hosts_cnt":0,"calls_content":"79231920440","calls_cnt":0,"sms_content":"тест смс пересечение","sms_regular_value":"","sms_cnt":0}
```

3) **`gck_project_create` возвращает id** (см. `gck_api_log_2026-01-26_183343.txt`), поэтому “список проектов” для поиска id не нужен.
4) **Телефоны**: формат строго `79231920440` (11 цифр, начинается с 7).
5) **Есть метод получить проект по id**: есть рабочий пример `util_02_gck_project_dump.py` (полезно для проверки/контроля после создания).
